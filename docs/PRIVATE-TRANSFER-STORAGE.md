# Portable private-transfer storage: engineering contract

**Authority:** [MASTER-SPEC.md](../MASTER-SPEC.md) defines the durable product goal. [Issue #134](https://github.com/AChWorks/wp-ai-bridge/issues/134) owns the accepted transfer outcome, implementation cutline and unfinished acceptance. [Draft PR #170](https://github.com/AChWorks/wp-ai-bridge/pull/170) owns actual candidate code, exact HEAD, test evidence and readiness. This document defines the **implementation architecture and invariants**, not a statement that the candidate or any installed release satisfies them.

## Product and hosting contract

- Direct WordPress↔authorized AI/MCP client exchange must work without requiring a Gateway, host SSH/shell, cPanel/DirectAdmin/Plesk-specific steps, new manual directories, global `WP_TEMP_DIR` changes, `wp-config.php` edits or an extra daemon/database. Keep the public `private-transfer` action contract and existing purpose-specific authorized consumers; separately prove any AI-host-native attachment or Gateway handoff.
- WordPress determines the current site/blog, upload/content roots, capabilities, principal, installed providers and database identity. Respect custom paths, multisite, filesystem restrictions and actual host limits.
- Never put unencrypted private staged data, private source snapshots, WXR, manifests or recovery metadata in an HTTP-addressable path. An `uploads/private` name, random URL, chmod, `index.php`, `.htaccess` or CDN configuration alone does not prove privacy. Database persistence prevents direct static-file disclosure but is **not encryption at rest** and does not eliminate database, backup or SQL-log exposure risks.
- Use the existing WordPress Media Library for *explicitly publishable* media. Do not duplicate its object model or make private transfer a dependency of ordinary public Media operations. Executable ZIP installation, Source Editing and content publication each remain separate elevated native effects with explicit consent.
- Preserve zero-byte, binary, Unicode and multi-chunk exact SHA-256 semantics; the current opaque lease, site/blog, WordPress actor, OAuth client, purpose, permission revocation, per-message/aggregate configurable limits, cancellation, retention, authorization and truthful unknown-outcome behavior. Never promote a previously verified lease into authorization for a later revoked effect.
- Never manufacture success when PHP, database, filesystem, official Adapter, client, webserver or native provider cannot fulfill the contract. Identify the limiting hop and fail closed **before** any irreversible WordPress action when a safe route is unavailable.

## Re-verified candidate findings (code at PR #170 HEAD 254ff78)

These are **findings in the unmerged partial staging implementation**, not confirmed defects in published v0.6.5:

| Classification | Evidence | Required invariant |
| --- | --- | --- |
| **Confirmed — metadata/column drift** | DB `cancel()` changes `meta.payload_released` but `save()` updates only `received_bytes`, `state` and `meta`; the SQL `payload_released` field stays unchanged. Today's admission query excludes `cancelled` states, so do **not** claim this alone has already caused quota overadmission. | Persist and validate one consistent released/claimed state across receipt and physical SQL fields; test cancel/release, readback, admission and crash recovery. |
| **Confirmed — separate quotas** | FS `begin()` enumerates filesystem manifests under a file lock; DB `begin()` uses a DB advisory lock and counts DB rows only. | A single current-blog finite admission policy covers **all** outstanding valid leases, including existing FS leases, with one concurrency coordinator and no silent double booking. |
| **Confirmed — backend ambiguity/overhead** | DB `has_id()` executes a table-existence check plus ID lookup for multiple operations; it maps an unavailable/error result to `false`, which is indistinguishable from genuine absence. | Stable, unambiguous per-lease backend routing; separate not-found from unavailable/uncertain; avoid repeated full schema probes and unnecessary DB queries on every operation. Never misroute an existing private lease on backend failure. |
| **Confirmed — incomplete lifecycle** | DB implements staging `begin/append/status/verify/cancel` only. FS-native path consumers, outbound producers, `read/release/admin_release`, source binding, Media/text/WXR claims and finish/recovery are not DB-native. | Complete the **existing** logical lifecycle and one-way native-effect fence across every applicable consumer before public availability; unsupported paths remain fail-closed. |
| **Confirmed — idle cleanup gap** | DB deletes at most 32 expired staging rows per future DB `begin()`; no independent routine or complete uninstall/data-retention contract exists for newly created tables. | Bounded event-driven cleanup, explicit owner release, idle-site recovery, table/data lifecycle and safe retention of irreversible claims. A traffic-driven WP-Cron alone cannot promise wall-clock cleanup on a site with zero requests. |
| **Exposure/performance risk requiring validation** | DB chunks are inserted with `UNHEX(hex-encoded-byte-string)`; SQL text can contain reversibly encoded private content. Aggregate query size, `SAVEQUERIES`/query logs, maximum packet, memory doubling and shared-host DB storage limits are not proven safe. | Prevent confidential bytes in regular application/SQL diagnostic logs, account for backup/access policies, measure DB chunk/query/memory/storage overhead and fail before ambiguous writes or resource exhaustion. Do not describe BLOB storage as encrypted. |
| **Native Core and producer feasibility unproven** | Media invokes `media_handle_sideload()` using a scratch `tmp_name`; official `WP_Import::parse()` is passed a private file path; Source Editing uses `verified_private_source()['path']`; export producers use `Private_Artifact_Writer::begin()` and `wp_tempnam()`. A host whose available temporary tree is public cannot safely materialize plaintext private bytes there. | Prove genuinely host-neutral Native Media, WXR/source-consuming **and outbound artifact-producing** paths with real Core/Importer APIs, or report an explicit impossible/unsupported surface before claiming universal zero-config support. |

Targeted **DB staging** smoke evidence on disposable WordPress 6.9.4 and 7.1.3 / PHP 8.4 / MCP Adapter 0.7.0 covered 0-byte/1-byte/Unicode/binary data, SHA-256, offset replay/conflict, cancellation/expiry, revoked Builder grants and a foreign WordPress principal. Those runs did **not** establish independent OAuth-client isolation, site/blog isolation, concurrent admission, finished native effects, crash/multisite/webserver acceptance or release readiness. Exact current evidence belongs in the PR, not in a duplicated status diary here.

## Recommended smallest sustainable design

The desired shape is **one public facade + one durable per-blog lease/effect state machine + a private byte-store interface**. Do not implement a second Transfer API, Media subsystem, authorization engine, open-ended object-store framework or service.

1. **Freeze public identity and consent.** Every lease is an opaque 64-hex ID bound to actual blog/user/authenticated OAuth client and purpose. Backend ownership is chosen and persisted at creation, cannot change because temp paths, configuration or backend health change, and is resolved without ambiguity. Every read/append/cancel/consumer rechecks applicable authority. A missing DB table/lookup permission/error is an error, not proof the lease was a filesystem lease.
2. **Prefer one WordPress-DB-backed backend for *new* private payloads**, provisioned lazily with bounded chunks and no autoloaded multi-MiB options, **if** measured host resource limits and the pathless native-consumer feasibility gate pass. The current FS-backed leases continue through their original exact journal/claim lifecycle until safely finished, cancelled or conservatively reconciled; do not reserialize an already claimed effect or issue a replacement lease to dodge an unknown result. This reduces permanent dual-backend complexity and avoids requiring new out-of-content private directories. A separately justified, genuinely private filesystem/ciphertext optimization is **future optional**, not a second mandatory path.
3. **One cross-backend admission/receipt owner.** During compatibility with legacy FS leases, account for their active bytes/count/scratch under a common finite site-level policy before admitting new DB leases. One serializer must protect concurrent reservations; do not assume a DB-only lock automatically covers legacy filesystem writers or concurrent old-version processes. After old FS leases retire, keep the simpler single-backend path and remove transition-only work when safe.
4. **Explicit, monotonic lifecycle.** Distinguish `open → verified → preparing/committing → committed|observed|rejected`, `cancelled` and `payload_released` as actually applicable. A one-way, durable and independently readable claim is written **before** the native WordPress effect. On any uncertain commit/response, retain claim/receipt identity, report `outcome_unknown`, refuse blind retry and support existing narrow administrator reconciliation without leaking another principal's bytes. Do not expire or silently remove unknown-effect fences to reclaim storage.
5. **Keep readers/consumers abstracted by capability, not raw paths.** Prefer bounded byte-window, digest/stream and verified-snapshot operations, then use the WordPress/provider's supported native API. A native API requiring a physical path needs a demonstrated non-web-served, correctly cleaned scratch surface or a separately tested Core-compatible pathless integration. Never substitute a public upload as staging for private WXR/source. For intentional public Media effects, the *final* user-authorized Media Library object may be public; pre-effect staging must stay private.
6. **Lean bounded operations.** No whole-object Base64 inside a single MCP response, unbounded DB/FS scans on common reads, row-count-only physical capacity promises or unlimited TTL. Administrator settings control distinct finite message/chunk/object, aggregate active byte, session and retention budgets. Check actual DB packet/disk/memory and PHP/process/web/intermediary limits; reject accurately rather than hardcode an arbitrary unchangeable product ceiling.
7. **Lifecycle/operations.** Define ordinary completed/expired byte retention, cleanup triggers, bounded batch behavior, transient failure visibility, network/multisite site identity, uninstall retention/removal and recoverability. WordPress has traffic-dependent task execution; any requirement for a strict no-traffic deletion SLA needs an explicit alternative and decision, not an invented daemon. Never erase immutable one-way receipts merely because their private source bytes are released.
8. **Upgrade before optimization.** Avoid a destructive data rewrite of existing valid FS journals. Preserve source-version metadata and per-lease backend identity, prove v0.6.5 active FS resume/claim recovery with the new code, and document a verified rollback/roll-forward route. Older binaries cannot be assumed to interpret newly created DB leases; no unguarded downgrade claim.

### Why not the other paths?

- **Permanent automatic dual FS+DB admission:** attractive for fast large files but doubles quota, cleanup, and native-consumer recovery paths indefinitely. Keep it only if representative DB load/packet constraints prove a single DB backend materially unsuitable and the alternative's cross-host confidentiality is independently established.
- **Public uploads plus access-control files/chmod:** rejected; static servers/CDNs can bypass PHP and server-specific rules.
- **A new daemon, external database, object-storage credential, host-panel/SSH prerequisite or mandatory manual `WP_TEMP_DIR`:** outside the accepted default installation.
- **Whole-file MCP JSON, generic raw filesystem endpoints, direct arbitrary SQL/command/PHP execution:** not a safe or host-neutral solution.
- **Full custom WordPress Media or WXR business implementation:** duplicates Core/provider authority and creates avoidable maintenance risk.

This is a **preferred engineering direction, not an assertion that pathless WordPress import has been proven or that the existing mixed candidate must be blindly rewritten**. Validate the smallest representative end-to-end consumer and shared-host DB viability first; then freeze the selected storage mechanism and any owner-level migration/security tradeoff **before** implementation.

## Development cutline and acceptance order

**Gate A — feasibility and backend choice (no production):**
- On disposable WordPress with `get_temp_dir()` under public `WP_CONTENT_DIR`, demonstrate confidential inbound binary staging and an authorized **nonempty** native Media effect; demonstrate WXR official importer or Source Editing *plus a private outbound artifact producer* without leaking pre-effect bytes. WordPress Media intentionally refuses a zero-byte sideload: test 0-byte **staging/verification** separately rather than claiming a 0-byte media attachment is valid. Confirm supported Core/provider semantics, not just mocks or assumed stream-wrapper support.
- Compare representative 0 B, 1 B, 128 KiB, multi-MiB and configured large-enough samples; measure query count, SQL payload/log handling, memory, packet bound, request duration and DB growth. If the preferred DB-only path cannot honor the accepted user workflow, stop and return the concrete feasibility contradiction and safer alternatives to Issue #134 rather than claim universal support.

**Gate B — correct shared storage semantics:**
- Fix physical-column/metadata consistency; implement stable tri-state backend routing and one unified quota/admission policy including legacy FS/DB. Cover new lease, old lease, cancel, expiry, read, release, clock/host failures, idempotent offset replay, and database/FS unavailable mid-request.
- Preserve authorization at each step, including wrong WordPress actor/blog/OAuth client and revoked capabilities; test same-site concurrent admissions (including one FS legacy session), interrupted writes and absence of unprotected private paths.
- Resolve retention and activation/upgrade/uninstall semantics with no hidden data loss and no unbounded DB growth. Confirm backward-compatible public receipt formats.

**Gate C — complete native consumers:**
- One full authenticated direct MCP Media import/export roundtrip and native text CAS first; WXR import/export and Source Editing follow through the same byte/claim mechanism, with exact preview/candidate binding, no blind native replay, true `outcome_unknown` recovery and no new WordPress feature logic.
- Test full incoming/outgoing byte integrity, direct HTTP/static/CDN exposure, Apache plus a different static-serving stack, moved content/uploads, multisite, restricted `open_basedir`, actual resource limits and existing ordinary Media/REST/OAuth/Workspace regressions. Test clean installs and installed-version updates with data preservation.

**Gate D — final acceptance and release:**
- Build/inspect the exact installable ZIP. Complete repository-required PHP/WordPress/official Adapter regression suites and exact-candidate CI. Perform a genuinely author-separated HIGH_ASSURANCE review of the final effective diff and remediate confirmed issues.
- Keep PR #170 Draft and Issue #134 OPEN until complete. Main merge, GitHub release, real-site installation and WordPress.org submission each require their **separate** gates; none is implied by a green staging test.
