# Private transfer storage and native WordPress consumers

**Owners:** [MASTER-SPEC](../MASTER-SPEC.md) defines product behavior; [Issue #134](https://github.com/AChWorks/wp-ai-bridge/issues/134) owns unresolved end-to-end acceptance. The implementation and exact-head evidence belong to [PR #170](https://github.com/AChWorks/wp-ai-bridge/pull/170). The adjacent public Media/package temporary-input hardening belongs to [#173](https://github.com/AChWorks/wp-ai-bridge/issues/173).

## Accepted outcome and boundaries

- Authorized clients exchange exact text, arbitrary binary, Media and WXR in both directions using WordPress's current site, principal, OAuth client and purpose-bound Bridge permissions. Direct authenticated MCP/HTTP access must not depend on Gateway, SSH, a host control panel, manual global `WP_TEMP_DIR` edits, an extra service or operator-managed private directories.
- Keep the existing public `private-transfer` actions, finite administrator-adjustable object/chunk/message/concurrency/retention limits, SHA-256 and exact-offset replay, revocation and already-verified native consumer contract. Native Media, official WordPress Importer, source editing/CAS and extension installation remain under their own WordPress authorization; transfer staging itself performs none of those effects.
- Private pre-effect payloads, WXR, source bytes and recovery/lease records must never be static-HTTP accessible. An `uploads/private` folder, PHP access checks, chmod, `.htaccess` and random URLs do not prove confidentiality across Nginx, LiteSpeed or CDN aliases. No new public file API, WordPress Media clone or private ZIP uploader.
- Native effects retain the existing durable one-way effect claim, uncertain-outcome handling and narrow administrator reconciliation. Older valid filesystem leases cannot be silently migrated, reissued or replayed after an upgrade.

## Selected minimal implementation — filesystem-native with automatic safe temporary selection

The published v0.6.5 already has a persistent 0700 per-site private temporary lease directory, finite admission/byte accounting, source-bound file readers and native effect journals. Native Media, WXR and Source Editing require **real local paths**. Reusing this proven lifecycle is safer and smaller than maintaining a second unmerged database-only lifecycle.

The current candidate shares one internal `Safe_Temporary_Staging` resolver: first use WordPress `get_temp_dir()` **only if canonical and outside known served WordPress/site/content/uploads/document roots**; otherwise try a writable PHP OS temporary directory or `upload_tmp_dir` that passes the same check. No user-supplied paths or URL are accepted. Existing safe WordPress temp selection is preferred so old FS lease identity does not move unexpectedly. The per-site lease directory is created by the plugin itself with mode 0700; temporary source/artifact files are mode 0600 before payload writes. This is **no operator setup**, not a demand to create/manage a folder in a host panel.

The separate Media and approved external ZIP input paths also use this private allocator (#173). The native WXR artifact producer and private transfer engine use the same validated directory; WXR structural preflight checks the actual selected private directory, not an assumed `WP_TEMP_DIR`. The originally published native WordPress consumers, claim state, policy and endpoint contracts are reused without a second storage backend.

**Fail-closed boundary:** if all PHP-writable temporary paths are also known to be web-served, a confidential file cannot be safely materialized for these native providers. Reject before writing sensitive bytes or performing a native effect; report the unavailable safe temporary storage rather than claim universal compatibility. PHP cannot discover every arbitrary webserver/CDN alias; such mappings need explicit hosted acceptance. Standard `open_basedir`/PHP/WordPress restrictions continue to apply. This release candidate cannot promise an unsupported host will work without a genuinely private temp path.

## Why the unmerged DB staging prototype is not the shipping route

The earlier PR #170 *unmerged* InnoDB fallback supported only `begin/append/status/verify/cancel`; it lacked native Media/WXR/source claims, reads, retention and one shared quota. Its `UNHEX(bin2hex(payload))` SQL literal was **confirmed recoverable** from `SAVEQUERIES` in disposable WordPress 6.9.4 / Adapter 0.7.0 ([Gate A evidence](https://github.com/AChWorks/wp-ai-bridge/issues/134#issuecomment-6203871894)). Encrypted DB bytes might mitigate query-log exposure, but cannot eliminate the physical scratch/native one-way-effect requirement; it also introduces key, schema, upgrade, transaction and storage-management complexity. The prototype never reached `main` or a release. It is removed from the current effective candidate, not converted into a hidden long-term second backend.

## Verification and integration gates

- On disposable **real WordPress** with `WP_TEMP_DIR` deliberately pointed at an HTTP-served content directory, prove (a) fallback stays off served roots, (b) binary/Unicode/zero-length staging and exact digest, (c) OAuth actor/site/client isolation and permission revocation, (d) native Media inbound/outbound, (e) Core WXR export and private importer/preflight with no public bytes, (f) text CAS and Source Editing one-way effect/recovery where applicable.
- Validate actual hosted resource constraints: available disk/space, `open_basedir`, custom WordPress paths and uploads, symlinks, multisite blog identity, two different static server configurations, safe rejection when no private temp is available, interruption/cleanup and v0.6.5 active-lease continuity. Never turn unit mocks into claims of all-host compatibility.
- Compare real receipt/client-native attachment boundaries: Bridge's private byte stream does **not** alone prove the AI client's UI or Gateway produced/downloaded a native file. Separate Gateway integration is not required for direct Bridge correctness.
- Finish final installable ZIP, source/static/unit/WordPress/Adapter checks on the frozen candidate and an **author-separated** security review. Keep Draft until those gates pass. Any main merge, GitHub Release, production deployment or WordPress.org submission follows its independent owner and safety gate; optional directory eligibility is [#171](https://github.com/AChWorks/wp-ai-bridge/issues/171).

**Recovery:** Trust current GitHub Issue/PR/commit/test artifacts, not historic chat summaries. On an unexpected missing legacy lease, database mismatch, access change or unknown native effect, refuse blind retry and preserve the existing recovery evidence; do not invent a successful migration or file publication.
