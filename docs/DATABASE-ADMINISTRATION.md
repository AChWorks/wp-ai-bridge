# Installation database administration

The database contracts described here are included in v0.7.0. A published release, an installed site, MCP exposure and a successful authorized operation are separate facts. Check the actual target build and grants before relying on these tools.

## Authorization and scope

Six independent administrator grants live in the dedicated native `wp_ai_bridge_database_access` option/settings group:

| Grant | Authority |
| --- | --- |
| **Database Inspection** | Discover table, column and index metadata without record/default values. |
| **Sensitive Database Read** | Read exact raw values, including possible credentials, OAuth state and private plugin data; also requires Inspection. |
| **Database Write** | Use typed describe/row-state, staging, insert/update and recovery actions; requires Inspection and Sensitive Read. |
| **Database Delete** | Additionally permit a batch containing delete, destructive schema work or destructive receipt recovery; requires the other existing grants. |
| **Database Schema** | Execute the separately typed schema contract; requires Inspection, Sensitive Read and Write. Destructive shapes/recovery additionally require Delete. |
| **Native Account SQL** | Separately server-enabled native-account statement execution and private results; requires every database grant including Schema, actual native authority and explicit per-request account-scope acknowledgement. |

All six default off on fresh installation and upgrade. Existing all-enabled ordinary settings do not enable them. Ordinary `wp_ai_bridge_settings` saves never rewrite the protected row; injected or older embedded database bits are ignored and are not migrated into authority. The always-registered protected option sanitizer and separate form capability enforce configuration authority beyond the settings screen. Uninstall removes this grant option along with disposable Bridge settings.

The connected native WordPress principal needs `manage_options`. Multisite additionally requires actual Super Admin and `manage_network_options` for both configuration and execution; site administrators cannot infer ownership of shared/network/other-blog tables from a prefix. Local administrators retain ordinary site-setting controls while database controls are disabled. Each complete required grant conjunction is evaluated from one current policy snapshot. Permission and execution callbacks recheck authority; database staging also reauthorizes its stored purpose, site, principal and authenticated client. OAuth identity, scope, approved-client revision and token revocation remain owned by the existing transport. Direct native Ability calls use the actual current WordPress principal, without inventing an OAuth client.

Database Write is powerful raw storage delegation: account, role, session and ordinary plugin-secret data are intentionally within its scope. It does not run the owning WordPress/plugin business lifecycle. Prefer the matching native feature for validation, hooks, caches, revisions or provider invariants. Bridge's own authorization, OAuth, recovery, audit and Workspace control state is protected from this ordinary typed-write contract.

Inspection, exact reads, typed row writes and typed schema operations target only the current WordPress database and exact installation-base-prefix persistent base tables. This includes dynamically discovered plugin and network/other-blog tables for an authorized Super Admin. These typed contracts have no database selector, alternate connection/credential input, view execution or caller SQL. The separately server-enabled native-account contract below has a deliberately different scope. Correct connection/prefix ownership is a deployment prerequisite, not a cryptographic tenant guarantee. The read tools remain live SELECT contracts; their preflight is not a concurrent-DDL isolation guarantee. Typed writes have the additional compatibility and transaction conditions below.

## Metadata: wp-ai-bridge/database-inspect

Input action tables supports limit and after_table (the previous returned table name). It returns installation base-table metadata, approximate engine row counts and keyset continuation without scanning record values. Input action schema requires table, supports section columns or indexes, limit and offset, and returns next_offset/has_more.

Column metadata preserves native data_type and bounded sql_type definitions, with sql_type_bytes/sql_type_truncated. Large ENUM/SET definitions are reported as truncated metadata, not falsely complete schemas. Use action column_type with table, column, offset and optional length to retrieve the complete definition through bounded base64 cell windows. It returns total bytes, SHA-256, data_type and continuation; positive byte offsets require expected_sha256. Reconstruct and verify the complete bytes exactly as for record cells, while retaining metadata-only authority. Concurrent DDL can stale the definition; restart on a hash conflict.

## Values: wp-ai-bridge/database-read

The rows action requires table and a nonempty columns array. Select only relevant fields. Optional filters maps exact column names to canonical base64 strings, or null for SQL NULL; matching is byte-exact in addition to native indexed equality. There are no caller-selected query expressions or functions.

Each returned item has a key map containing complete base64-encoded primary-key values and a cells map for the requested columns. Primary-key bytes are also bounded in SQL: an oversized TEXT/BLOB prefix-index key is omitted from key, key_complete becomes false, and key_hashes carries its full SHA-256. Pass both key and key_hashes to a later cell request; a hash match must still identify exactly one current record. Hash-key lookup can scan/hash the table and does not claim indexed-lookup performance. Each cell reports sql_type, is_null, encoding=base64, data, bytes, total_bytes, offset, sha256 and next_offset. The key, key_hashes and cells dictionaries are JSON objects, including empty dictionaries and quoted numeric column names. Native PHP results use stdClass for those dictionaries. Numeric input-map keys are normalized to exact string identifiers; names such as0 and01 remain distinct, with no aliases. Native standard objects and decoded associative maps are accepted as selectors. Decode base64 to recover exact database bytes. BIGINT/DECIMAL values are bytes, never PHP/JavaScript numbers; NULL and empty strings remain distinct. Serialized PHP values stay opaque and are never unserialized.

For one integer primary key, continue with returned after_id, preserving the table, projection and filters and leaving offset unset. This uses exact DECIMAL comparison beyond PHP/JavaScript integer ranges. Composite/text keys and keyless tables use next_offset with paging=offset_live; concurrent inserts/deletes may skip or repeat records. All pages are live reads, not a snapshot, export or transaction.

The cell action requires table and column, plus either nonempty key/key_hashes selectors or explicit row_offset with the expected cell hash. key uses canonical base64/NULL; key_hashes maps exact columns to 64-character lowercase SHA-256 values. All predicates are combined. The key must match exactly one current record. This may be a full returned primary key or a unique predicate for a keyless table. Duplicate/absent matches fail under key mode. For a keyless/duplicate table, use explicit row_offset addressing instead of key/key_hashes, include expected_sha256 even for the first byte window, and preserve the original row-page filters if any. Offset-live items report their absolute row_offset. The server selects that filtered ordinal first, then compares the selected cell hash; the expected hash never changes which ordinal is selected. A matching hash proves the intended cell bytes, not a stable physical row identity. Refresh the page when the position disappears or its value changes. Optional length selects a bounded SQL window, offset defaults to zero, and expected_sha256 is mandatory when offset is positive (and always for positional reads). Reuse the previous cell hash for every continuation and verify the reconstructed bytes against it. A changed value returns database_cell_stale; restart instead of mixing versions. An offset beyond the value is an error.

## Read capacity, evidence and diagnostics

Page/projection/window limits and aggregate projected-cell budgets derive from the existing administrator response policy; there is no aggregate table/record/value/operation-count ceiling in these tools. The server bounds bytes in SQL before PHP receives them. Record-cell/type-definition requests can read up to one quarter of the configured response bytes per SQL window; the default requests that same bounded window. The wrapper adaptively trims its returned byte prefix to fit the actual duplicated/escaped MCP envelope, updating bytes and next_offset without another query or full-value hash. Three-byte Base64 boundaries keep the fitting search monotonic. Client-requested shorter windows remain supported. The wrapper checks the projected MCP envelope and explains how to request fewer fields/rows, a shorter window or a different response budget. A bounded response is not a promise that an intermediary accepts the same capacity.

The database hashes the full selected value to detect changes even though PHP receives only its window. This costs database CPU for large values and every continuation revalidates it; it is not a frozen export lease. Integer keysets avoid offset scans; other pagination is explicitly weaker. This contract does not claim snapshot consistency, queue-business lifecycle execution, hooks/cache invalidation, or visual-editor parity.

Sensitive reads use the existing bounded Bridge activity store with timestamp, principal, client fingerprint, action/table fingerprint, unique event reference and outcome; no row values, keys, SQL or credentials are logged. A failure to persist audit metadata prevents returning raw values. This is the existing finite operational history, not an immutable archival audit system. Database query failures preserve actionable privilege/availability guidance while excluding data-bearing SQL/error text. Database/server diagnostics remain the owning source for deeper failures.

Generic registered REST remains a separate high-trust surface. Its excluded Bridge/control-plane routes cannot invoke these database tools; existing provider permission callbacks and protected-lifecycle requirements remain unchanged. Database grants do not enable generic REST and generic REST consent does not directly enable these tools.

## Typed writes: wp-ai-bridge/database-write

This single public Ability is statically non-readonly, destructive and non-idempotent, including describe, row-state and staging requests. A read-looking action does not lower the trust required by the mixed surface.

| Action | Required input beyond action | Contract |
| --- | --- | --- |
| `describe` | `table` | Current schema hash, ordered primary-key names and typed-write compatibility information; complete metadata remains in database-inspect. |
| `row_state` | `table`, complete `key` | Current schema/state hashes for exactly one live row, without complete stored values. |
| `execute` | `operation_id`, ordered nonempty `operations` | One insert/update/delete batch with atomic transactional row changes and its committed result receipt. |
| `recover` | `operation_id`; optional `destructive` | Historical committed receipt under current authority, or an explicit not-recorded/uncertain result. A delete receipt requires `destructive=true` and current Delete consent. |

Each batch step has `action`, `table` and `expected_schema_hash`. Insert also requires a `values` object, which may be empty for a supported all-default/auto-primary-key insert. Update requires `key`, `expected_state_hash` and a nonempty `values` map; delete requires `key` and `expected_state_hash`. Unknown fields and unsupported actions are refused. No SQL fragments, expressions, upsert, replace, error suppression or partial-success mode are accepted.

Map keys are exact column identifiers, including quoted numeric names such as `0` and `01`. Values and complete key components use canonical Base64 strings, JSON `null`, or a verified staged descriptor:

```json
{"transfer_id":"<64 lowercase hex characters>","total_bytes":4194304,"sha256":"<64 lowercase hex characters>"}
```

Staged descriptors are supported for the TEXT and BLOB families, including complete keys of those types. Other supported scalar columns use inline Base64/NULL.

JSON numeric scalars are never SQL values: BIGINT and DECIMAL must retain their exact byte representation. NULL, empty bytes, an omitted insert column and an omitted update column are distinct. Serialized PHP is opaque and is never unserialized. Supplied data must match the SQL-visible stored bytes/NULL after DML; any warning or normalization mismatch aborts the batch, including silent rounding, padding, truncation or character conversion. This is exact SQL-visible representation, not a claim about an engine's physical on-disk encoding.

### Keys, state and insert results

Update/delete require every current PRIMARY KEY component with complete bytes. The read tool's `key_hashes`, arbitrary predicates and live row offsets are not mutation identities. A staged descriptor supplies the complete oversized key, including a TEXT/BLOB prefix-index key; it is not a hash-only selector. Missing, duplicate or stale matches fail. Native indexed equality narrows candidates and byte equality prevents collation-equivalent values from being adopted.

Use the typed tool's live schema/state hashes, not a read-cell SHA-256. The versioned state identity covers the schema and every stored column's typed NULL or complete byte length/hash, including fields omitted from a read projection. Large values are hashed by the database without loading their complete contents into PHP. The writer pins the current table/schema, locks and rechecks the exact row inside its transaction. A returned hash can become stale immediately after another authorized writer commits.

Insert requires explicit non-auto primary-key components; one eligible auto-increment component may be omitted. Its generated ID is retained as an exact decimal string, never a PHP/JavaScript integer. Omitted ordinary fields use supported native defaults; `values={}` is valid when every required non-auto key/default condition is satisfied. Supplied fields are verified before commit. Update cannot change primary-key columns. Unsupported generated/expression types or an insert whose resulting primary key cannot be established fail explicitly under the current package's type contract.

An update whose supplied bytes already match the locked row still checks both stale preconditions, returns a verified no-op and issues no UPDATE. A missing row is not a successful delete. A duplicate insert or failed later step rolls back the batch's transactional row changes. Auto-increment allocation gaps are outside this row-atomicity guarantee.

### Resumable large values and keys

Database staging reuses the existing private-transfer storage, with the fixed purpose `database_value`; it does not relax generic media/source transfer consent.

| Action | Required input beyond action |
| --- | --- |
| `stage_open` | `total_bytes`, complete `sha256` |
| `stage_append` | `transfer_id`, byte `offset`, canonical `content_base64` |
| `stage_status`, `stage_verify`, `stage_cancel`, `stage_release` | `transfer_id` |

Open returns the private transfer ID, current request/chunk/file/reserved-byte/session/lease policies and received progress. Append retries must match already acknowledged bytes; changed or overlapping bytes fail. Verify requires complete length and SHA-256. No append is accepted after verification. Cancel/release removes disposable staged input and does not undo or release a committed database receipt. No caller path, URL, public file or filesystem descriptor is returned.

A new effect opens and verifies every referenced source under the existing owner/site/client/purpose coordination before transaction entry. The internal consumer holds safe source descriptors and feeds bounded chunks through native prepared `send_long_data`, then executes each DML statement once. It does not load an entire BLOB/key into PHP or expose partially written target values. Uploading or verifying a stage changes no target row, and no database transaction stays open across HTTP requests.

Staging uses the existing administrator transfer policies and actual disk capacity. Encoded database input uses the existing Transfer Settings request-byte policy, independently of registered REST setting-value limits. Response output uses the existing response-byte policy. Schema and compact-receipt processing use the larger of those request/response budgets, capped at one eighth of known finite PHP memory; if no finite memory bound is known, the larger transport budget applies. Streamed cell/key bytes have no whole-value processing-budget cap: their staging, column and native packet constraints govern instead. These are current resource/message/processing policies, not a fixed full-record, table-size, total-data or lifetime operation-count ceiling. Server column limits and `max_allowed_packet` still apply to complete native parameters: chunked transport does not bypass them. A size/budget error explains the relevant setting or host constraint rather than silently truncating or splitting one atomic batch. Release unused staged bytes when finished.

### Transaction ownership, receipts and recovery

The typed executor retains Core's existing `wpdb` mysqli/mysqlnd connection and selected database. It creates no second connection and reads no credentials. Database drop-ins, custom routing/subclasses or an unverifiable physical handle fail with compatibility guidance. It bypasses `wpdb` reconnect/retry behavior, query filters and ordinary query logging/counters; it captures native warning/affected-row/numeric failure data and emits compact outcome metadata.

The supported session begins with autocommit, foreign-key checks and unique checks enabled and no ambient active transaction. An unqualified next-transaction isolation guard is followed immediately by temporary `SET autocommit=0`. There is no `START TRANSACTION` that would release an existing explicit SQL table lock. Only the owned work is terminated with `COMMIT/ROLLBACK AND NO CHAIN NO RELEASE`; original autocommit=1 is restored only after acknowledged termination. Uncertain mode/termination cleanup quarantines the handle rather than risking an implicit commit. The guard may replace an earlier pending next-transaction isolation override; inherited read-only mode is not silently disabled.

Sources and current authority are validated before entry. Authorization linearizes immediately before the transaction; this does not promise instantaneous cancellation when a grant/token changes during an already-running transaction. No WordPress hooks, query callbacks, application callbacks, reconnect, statement resend or commit retry occur inside the owned critical section. Each native call also isolates PHP diagnostics behind a fixed internal error handler through stream/result cleanup and restores the caller handler in an exception-safe finally boundary. This prevents data-bearing MySQLi warnings from dispatching application callbacks even when ERROR reporting is enabled without STRICT; the caller MySQLi report mode is preserved.

`operation_id` is mandatory: 8–128 ASCII letters, digits, underscores, hyphens, dots or colons. The receipt identity binds version, site, actual principal, authenticated client and ID. Its canonical request fingerprint preserves ordered operations, exact identifiers/preconditions and typed scalar NULL or complete length/SHA identity. Equivalent inline or restaged bytes have the same identity; changing only an expired transfer ID cannot authorize a second effect.

A plain unique receipt INSERT is the first DML. Target changes and the final compact result/redacted event are committed in that same verified InnoDB transaction. Concurrent same-ID attempts arbitrate on the native unique key. A committed duplicate returns only the fingerprint-matched historical result, even after target deletion/change or staging expiry; it does not re-execute or claim that the historical state is still current. A conflicting request cannot adopt that committed identity. A confirmed rollback leaves no committed receipt and permits a deliberate same-ID, identical-request retry.

A recovery lookup that finds no committed row reports `not_recorded`. Absence is not proof that another request is not currently in flight. After a lost/ambiguous reply, retain the same ID and request, recover authoritative status and never substitute a new ID or blindly resend SQL. A failed COMMIT reply remains unknown even if later rollback cleanup succeeds. Committed identities have no generic-create count admission quota or recovery expiry; storage failures remain real capacity errors. If later request/response policies or PHP processing capacity cannot return the retained compact result, restore sufficient relevant capacity rather than truncating the result or executing again.

### Eligible effects and protected state

Current typed support requires persistent installation-prefixed base tables, InnoDB target/receipt storage, an identified primary key and verified native metadata. Supported scalar families are integer, DECIMAL/FLOAT/DOUBLE/BIT, CHAR/VARCHAR/BINARY/VARBINARY, TEXT/BLOB, DATE/DATETIME/TIMESTAMP/TIME/YEAR and ENUM/SET. JSON, spatial/unknown types, any generated column or CHECK constraint are outside this package's verified schema contract. Temporary shadows, views, nontransactional engines, target/receipt triggers, unavailable trigger visibility and unrecognized executable schema/default expressions fail explicitly. Literal/NULL defaults and narrowly recognized native CURRENT_TIMESTAMP forms are the supported default class. Complete type/compatibility decisions come from describe/current execution, not a guessed parser for arbitrary SQL.

Trigger visibility requires a provable current-account native grant; an empty privilege-filtered listing does not establish absence. The implementation is conservative about role-only and partial-revocation configurations. DELETE and UPDATE of indexed columns additionally need complete native InnoDB FK graph visibility—MySQL `INNODB_FOREIGN` or MariaDB `INNODB_SYS_FOREIGN` and the corresponding metadata privileges—and reject the table's mutating inbound CASCADE/SET NULL rules for the corresponding operation. This is conservative for an indexed update: an unrelated indexed column does not bypass the incoming-rule check. Inserts and exclusively non-indexed updates cannot initiate those cascades; ordinary restrictive FK checks remain native. The tool does not disable checks, acquire another account or silently expand to an unverified effect graph. FK identity proof currently requires lower_case_table_names=0. MariaDB converts both schema and table through its native filename character set, verifies a lossless round trip and positively resolves the InnoDB dictionary entry before matching the complete graph. Unverified case modes, legacy names or unresolved partition/dictionary representations return database_write_fk_identity; an empty match is never substituted for a failed identity proof. Native filename conversion is documented by [MariaDB](https://mariadb.com/docs/server/reference/sql-structure/sql-language-structure/identifier-to-file-name-mapping).

Locked control guards protect old and proposed native-collation identities across installation blogs: Bridge options/settings/grants/capacity policies, OAuth/transient/client state, audit, create/cron/database receipts, source locks and Workspace canonical post/meta state. Renaming a row into or out of a protected name cannot bypass the guard. Ordinary plugin secrets remain deliberately writable under the sensitive/write grants. These are current-package supported boundaries, not permanent exclusions from the accepted full administration outcome.

Results use `format=wpai-database-write-v1`. Describe returns `primary_key`, `compatible` and `compatibility`; row_state returns `schema_hash` and `state_hash`. A committed result has `status=committed`, `historical`, `operation_ref`, `steps`, `audit` and post-commit `reporting_pending`. Step outcomes are `inserted`, `updated`, `deleted` or `unchanged`, with `affected`, decimal-string/null `auto_id` and current/null `state_hash`.

The atomic receipt carries the essential redacted event, operation reference, compact per-step outcomes/affected counts/generated IDs/state hashes and historical status. It contains no submitted values, raw keys or SQL. The existing finite Activity log is a post-commit projection. Failed Activity/cache/session reporting after an acknowledged commit remains committed with reporting pending; it must not become an ordinary retryable mutation failure.

## Validation and remaining coverage

The read regressions cover grants/revocation, native/MCP/multisite scope, schema/rows, exact bytes, pagination/windows/staleness and payload/audit behavior. Typed-write acceptance additionally requires native and authenticated MCP execution, actual multisite authority, schema/row concurrency, protected renames, exact normalization/no-op semantics, 4 MiB staged values and oversized keys, atomic last-step rollback, receipt arbitration/recovery and connection/COMMIT ambiguity on genuine MySQL and MariaDB. Source, fixtures, passing exact-candidate checks, independent review, release and installed-client execution are separate evidence; this documentation does not claim pending checks have passed.

[Issue #199](https://github.com/AChWorks/wp-ai-bridge/issues/199) records the accepted administrative program and its validation. Version 0.7.0 also includes the separately delegated native settings, logs, scheduler, scoped filesystem, configuration/Customizer and complete database/files capture with isolated restore contracts documented in [Administration](./ADMINISTRATION.md). Typed storage access does not itself prove a provider business lifecycle or live disaster-recovery workflow.

[Native Options](NATIVE-OPTIONS.md) separately documents effective native site/network reads and private snapshot export. [Native option mutations](NATIVE-OPTION-MUTATIONS.md), included in v0.7.0, adds one native add/update/delete family, inert complete-value inputs and historical status. It uses Core callbacks with a durable one-dispatch fence, without the typed database writer's atomic target-and-receipt transaction. Raw database writes do not supply native settings lifecycle semantics; the two contracts must not exchange staged input purposes.


## Typed schema: wp-ai-bridge/database-schema

The separately default-off Schema grant enables a mixed, non-readonly, destructive and non-idempotent Ability. All requests also require current Inspection, Sensitive Read, Database Write and actual administrator/network authority. Drop, truncate, modify/drop columns and removal of indexes/constraints additionally require Delete; recovery requires Delete because an old receipt may describe a destructive operation.

Actions are describe(table), execute(operation_id,operation) and recover(operation_id). One execute request contains one complete typed operation: create_table; add_column, modify_column, drop_column or rename_column; add_index/drop_index; add_foreign_key/drop_foreign_key; rename_table; drop_table; truncate_table. Every existing target requires its current schema hash. Creation explicitly expects absence and never adopts an existing table with IF NOT EXISTS.

Column definitions use exact name, a finite native type, native length/precision/scale where applicable, nullable, optional unsigned/auto_increment, canonical Base64 literal default or NULL, ordered ENUM/SET members and explicit charset/collation. Definition fragments, executable default/generated expressions, alternate engines, paths, temporary tables and CREATE-AS-SELECT are absent. Native validation still owns type ranges and compatibility. Current text/default literals require valid UTF-8 and a supported native UTF-8 client charset; binary/expression-default shapes outside that representation return a compatibility/input error rather than silently changing bytes. New tables use InnoDB. Existing generated/versioned or CHECK-expression schemas are not rebuilt through an unproved compiler path. Ordinary index work does not inherit the typed row writer's PK, trigger-free or global FK-visibility prerequisites.

Schema mutations protect entire control dependencies across installation blogs: options, sitemeta, blogmeta, posts, postmeta and Bridge-owned table namespaces. Unlike row writes, DDL cannot exclude individual protected rows. Foreign keys created by this typed surface must also reference non-control installation tables. Native FK/unique checks remain enabled. Drop and truncate retain the engine's native inbound-FK veto; no checks are disabled and no external FK-absence claim is inferred from an empty privilege-filtered view.

Describe reports precondition_strength=observed_not_atomic. Exact native metadata and SHOW CREATE hashes are observations, not a universal schema CAS. DDL normally implicitly commits and cannot be enclosed in the row writer's atomic receipt transaction. A native OK plus warnings remains acknowledged; it never becomes a claimed rollback when audit, inspection, cleanup or final-receipt persistence later fails.

Rename has a separate operation-specific fence. Supported native families acquire an owned WRITE table lock after clean-session admission and durable arming, recheck the exact definition and complete native FK graph while the lock remains held, refuse any existing inbound/outbound FK dependency, execute the generated rename once and release only the acknowledged owned lock. This blocks external replacement or a newly added inbound FK during the supported rename critical section. MySQL 8.4 table/column rename and MariaDB 11.8 column rename are qualified shapes; unproved engine/version/table-rename combinations report database_schema_exclusive_ddl_required. This is not a universal LOCK TABLES guarantee or a permanent prohibition on legitimate rename administration.

MariaDB 12.3 currently lacks an operation-specific rename fence qualification. Its typed rename requests return precondition=unproven_engine_specific_rename_fence with the observed native_version before journal reservation, arming or DDL dispatch. Qualification for that series requires independent-session evidence of the complete native critical section. Administrators may issue a separate native-account SQL request under the server enablement, complete consents, account-scope acknowledgement and resource requirements below.

The shared internal Administration_Operation_Journal has fixed server-owned schema/filesystem/scheduler/configuration/customizer purposes. Its identity binds scope/blog/network/user/client; SQL or raw values do not enter compact descriptors. It commits prepared, then commits dispatch_armed before exactly one native effect. Existing prepared, armed or completed receipts never issue a new dispatch claim. The original invocation may complete a known undispatched reservation; interrupted/armed/unknown identities never automatically resend. Recover returns the retained state. Observation of matching schema, absence or emptiness cannot establish who caused a change. Essential acknowledged native outcome remains visible even if reporting_pending is true.

## Explicit native-account SQL proposal: wp-ai-bridge/database-native-sql

This source contract introduces a deliberately broader access posture requiring explicit integration approval. It requires the hosting-side constant WP_AI_BRIDGE_ALLOW_NATIVE_ACCOUNT_SQL to be exactly true, every current database grant including Schema and Native Account SQL, actual administrator/Super Admin/network authority and acknowledge_native_account_scope=true on every request. Ordinary existing database grants cannot enable it.

**Native-account SQL is not installation-confined.** The existing WordPress account may have privileges over other schemas, routines, server files and Bridge authorization/recovery/control storage. This contract does not parse arbitrary SQL into a claimed sandbox. Hosting/account privileges remain the execution boundary. It creates no connection, credentials, PHP/shell proxy, reconnect or hidden multi_query execution.

prepare accepts operation_id, one canonical Base64 statement, ordered canonical Base64/NULL parameters and a finite max_result_bytes reservation. Native preparation validates one supported prepared statement and its pre-execution resource evidence. A fresh durable prepared receipt returns a random preparation_token once; only its hash is stored. execute requires that token and the identical statement/parameters/reservation fingerprint. Execute never creates or recreates a missing preparation. It CAS-transitions the existing prepared record to dispatch_armed with an acknowledged commit, then calls native execute exactly once. Existing armed/completed state returns historical information without another send.

Raw SQL may change or delete its own preparation/control storage. Consequently receipt availability is conditional, absence never authorizes execution, and this is neither an exactly-once nor an idempotency promise after control-store loss. A new explicit preparation is a new potentially consequential act. The API exposes native acknowledgement separately from SQL/business commit semantics, result completeness, reporting persistence and subsequent observations. No SQL or parameter values are placed in the compact journal or general activity log; numeric native diagnostics remain available. Session/control-namespace changes can quarantine the original handle.

Results use an already admitted private native_sql_result stream and never buffer an entire result set. Before dispatch, preparation requires finite known PHP headroom, bounded native metadata and an admitted row allocation. Known prepared result widths use the smaller of summed native declared field-byte maxima and max_allowed_packet; parameter-dependent/unknown field widths use the native packet fallback. The row allocation and metadata reserve must fit actual headroom. Unsupported pre-execution result shapes, including fieldless CALL/multiple-result paths, are refused before dispatch when no resource proof exists. A changed/expanded result shape is detected before row fetch and reported incomplete after preserving the native acknowledgement.

Native unbuffered fetch retains one admitted row at a time, then writes bounded JSON Lines frames to private storage. Fields carry exact Base64 names and native type/flags/charset/declared-byte metadata. Each cell carries row/column ordinal, typed NULL, full byte length/SHA-256 and Base64 windows. BIGINT/DECIMAL remain exact scalar bytes; native FLOAT/DOUBLE use big-endian IEEE-754 bytes with an explicit representation marker, avoiding PHP decimal rendering loss. A final complete marker and verified private-file SHA distinguish a complete result from partial output.

result_status, result_read and result_release use the same operation_id, private result_id, current server enablement/authority and account-scope acknowledgement. Positive result byte offsets require the expected whole-file SHA-256. Window lengths follow response capacity and the existing private-transfer policies. Reconstruct and verify the exact stream before interpreting it. Capacity/transport/fetch/cleanup failure after execution does not roll back acknowledged database effects and never authorizes resend. Unfinished raw native result handling quarantines the handle; increasing an ordinary result reservation cannot disable identity or unknown-effect fencing.
