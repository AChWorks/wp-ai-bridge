## Diagnose a missing operation without guessing

1. Identify the site's actual connection and deployment. The direct Bridge MCP server's `tools/list` deliberately exposes three **generic Adapter tools** (`mcp-adapter-discover-abilities`, `mcp-adapter-get-ability-info`, `mcp-adapter-execute-ability`), **not** individual WordPress abilities. Absence of `extension-lifecycle` from `tools/list` is expected, not proof of missing implementation. A Gateway or other client may present a different wrapper inventory; diagnose its route separately.
2. Through the authenticated connection, call `mcp-adapter-discover-abilities`; inspect the returned `abilities` and their exact names. Use `mcp-adapter-execute-ability` with `ability_name: "wp-ai-bridge/abilities-read"` and `parameters: {"action":"list","search":"extension-lifecycle"}` for bounded searchable WordPress registry inspection; use `{"action":"get","name":"wp-ai-bridge/extension-lifecycle"}` for the exact public input/output contract. The Bridge-owned registry exposes plugin/theme lifecycle regardless of whether its **execution** group is enabled. Do not call an install/activate/delete operation merely to test discovery.
3. Execute `wp-ai-bridge/bridge-info` through the same authorized Adapter route. It reports the **deployed** `plugin_version`, WordPress version, MCP Adapter availability/version, and enabled Bridge `access_groups` without credentials. `wp-ai-bridge/site-context` (Issue #110 implementation pending release) supports `{"section":"current_user"}` for native capability flags without enumerating providers; `{"section":"plugins","offset":0,"limit":25}` and corresponding collection selectors provide explicit bounded pages. Oversized legacy `{}` returns `projection.omitted_sections`, not silently empty inventory. This is not a comprehensive permission oracle or proof of Bridge delegation; verify the deployed Bridge version first. Compare actual versions/identities with the intended deployment before concluding an Ability is absent. Do not treat the repository's latest `main` or latest release as the installed site version.
4. For an actual requested operation, intersect Bridge grants with **that operation's current WordPress/provider authority**, site or network policy, and environmental dependencies. `abilities-read` explicitly returns `execution_permission: "not_evaluated"`: a public contract is not permission. For `extension-lifecycle`, enablement of `code_extensions` alone is insufficient without the action-specific native capability. An external HTTPS `package_url` additionally needs `external_packages`; deletion also needs `users_destructive`. These grants default off, and finding a registered Ability must never turn them on.
5. If discovery fails, classify the observed failure with evidence: wrong endpoint/identity; older deployed build; missing Adapter/provider; registered but not MCP-exposed; disabled Bridge delegation; current WordPress/provider denial; environment restriction; or genuinely unimplemented operation. For third-party Abilities, the provider's own MCP exposure metadata and permission callback remain authoritative. Do not fabricate an `unsupported` verdict from a single search result or report `supported_and_enabled` before the required checks.

## 2026-10-10 live evidence and follow-up decisions

The earlier source-only evidence matrix remains a **source snapshot**, not an assertion that the current release was deployed. The Alumni connection was re-inspected read-only: **WP AI Bridge 0.4.2 / WordPress 7.1.3 / official MCP Adapter 0.7.0**. Its `wp-ai-bridge/extension-lifecycle` contract is present and discoverable; Bridge `code_extensions`, `external_packages` and `users_destructive` groups all report enabled. **Neither actual native `install_plugins/install_themes` nor a package installation was exercised**, so an existing Ability and delegation setting are not proof of execution authority. The broad 100-item catalog query is still transport-bounded and returned `response_too_large`; prefer small catalog queries and exact names. The new `site-context(section=current_user)` capability checks on `main` (PR #111) require a separately approved release/deployment to become available on Alumni.

The new `extension-authorization` read-only contract (**integrated into `main` via PR #114; still pending release/deployment**) presents the **exact action-specific delegated group and WordPress native capability truth** without executing or installing. Unlike provider-wide semantic search it avoids false negatives from localized labels, and unlike broad registry inspection it evaluates only a fixed Bridge-owned lifecycle action. It returns `execution_permission:not_evaluated` even when the pure permission predicate passes: target, filesystem, network, actual Upgrader execution and package source are NOT tested. This does not replace `abilities-read` or any non-Bridge provider's own authority.

**Current architectural decisions:** [#108](https://github.com/AChWorks/wp-ai-bridge/issues/108) is integrated Bridge-owned private ZIP ingress through browser HTTPS staging, not Media Library or generic Gateway streaming; [#119](https://github.com/AChWorks/wp-ai-bridge/issues/119) has integrated filtered discovery and conservatively guarded local REST invocation, with broader acceptance still open (not arbitrary HTTP/PHP); [#112](https://github.com/AChWorks/wp-ai-bridge/issues/112) is CLOSED NOT_PLANNED because Core/specialized plugins—not Bridge—own **new role/capability definitions**. CPT/taxonomy definitions, forms, commerce, SEO, SMTP and backups likewise remain Core/provider/host-owned domain features, accessible through real authorized contracts. **Persistent Workspace remains deliberately Bridge-owned** for private, recoverable AI project continuity: no extraction or deprecation ([#116 closed](https://github.com/AChWorks/wp-ai-bridge/issues/116)). Cron/Core maintenance and WXR require verified native/provider workflows, not raw shell/database shortcuts; browser-rendered preview remains outside the WordPress PHP plugin. **#103 is complete** for AI-client-neutral foundations; #113 remains closed NOT_PLANNED for unselected vendor implementations. Gateway-side parity verification is separately scoped to [mcp-gateway#130](https://github.com/AChWorks/mcp-gateway/issues/130); only verified Gateway deficiencies require Gateway code. None of the upcoming code is a published release merely because it is specified here.
