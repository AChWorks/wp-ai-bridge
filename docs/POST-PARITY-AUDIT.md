# Administrator capability coverage — published source and live audit (#99)

**Evidence date:** 2026-10-10 UTC. **Published build:** [WP AI Bridge v0.5.1](https://github.com/AChWorks/wp-ai-bridge/releases/tag/v0.5.1), GitHub `main@09b79f9bb85f4bf4912e3084edafd8f2c4978be4`. **Read-only connected target:** owner-connected Alumni WordPress Target, WordPress **7.1.3**, installed Bridge **0.5.1**, official MCP Adapter **0.7.0**, confirmed through actual `bridge-info` execution. This is a **dated target-specific audit**, not a promise that every other installation has the same extensions, delegation or native permissions.

This is the canonical *capability matrix* for Issue [#99](https://github.com/AChWorks/wp-ai-bridge/issues/99). Historical pre-v0.5.1 investigation, missing-Ability observations, release-candidate and abandoned manual ZIP designs remain in that Issue's history, **not** as current implementation status. The architectural target is still [MASTER-SPEC](../MASTER-SPEC.md): enable the full range of legitimate WordPress administrator workflows through actual WordPress/Core/provider contracts, without inventing parallel domain logic, bypassing the principal's permissions or claiming that every wp-admin screen has an API.

## What “supported” means

Separate five proofs:

1. **Implemented in released source:** the Ability/contract exists in the published version, may be registered conditionally, and passes the appropriate source/CI tests.
2. **Discoverable on the actual Target:** present in that connected site's MCP-public native Ability catalog or indexed REST registry. Catalog presence is **not permission**. An item absent from the broad `tools/list` of the official Adapter may still exist in native `abilities-read`.
3. **Delegated:** the relevant Bridge administrator access group is enabled for the authenticated connection. New installations have only Site Read on by default; live settings may differ.
4. **Native authorization preflight:** the *current WordPress principal* has the operation-specific capability and applicable Bridge permission predicate passes, where a safe action-specific diagnostic exists. Even a passing preflight reports `execution_permission: not_evaluated`.
5. **Actual successful execution:** exact target, environment, provider permission callback, filesystem/network/site state and desired side effect were exercised and verified. **No installation, activation, deletion, import, Core upgrade or other destructive operation was executed on the live Alumni site as part of this audit.** Non-production CI/integration evidence is distinct from the live read-only audit.

If one layer is missing, classify it as old build, disabled Bridge grant, denied native/provider authority, missing/hidden registration, unsupported operation, inadequate client/Gateway transport, or host/browser boundary **with evidence**. Do not call a feature “missing” because a broad catalog response was truncated or because a client did not know the exact Ability name.

## Measured live evidence

- `bridge-info` succeeded and reports all **15 Bridge groups enabled** for this connection: Site Read, Builder Write, Remote Media, Live Content, Site Configuration, Advanced Metadata, Authentication & Credentials, Code & Extensions, External Packages, Source Editing, Native Abilities, Registered REST Discovery, High-Trust REST Invocation, Comments, and Users & Destructive. This is **site-specific** and does not expand WordPress authority.
- `site-context({"section":"current_user"})` succeeded: **all 14 exposed native capability flags were true**: `read`, `edit_posts`, `publish_posts`, `upload_files`, `manage_categories`, `manage_options`, `install_plugins`, `activate_plugins`, `install_themes`, `switch_themes`, `list_users`, `create_users`, `edit_users`, `delete_users`. This is **not** every WordPress capability, and says nothing by itself about multisite/Super Admin or filesystem readiness.
- `extension-authorization` returned `permission_preflight_passed` on **all nine valid plugin/theme lifecycle actions** (plugin install/update/activate/deactivate/delete; theme install/update/activate/delete), plus a separately inspected plugin install from `public_https`. This checks the action-specific WordPress capability (including `update_plugins`, `delete_plugins`, `update_themes` and `delete_themes`), delegation and pure permission predicate. **All ten were non-mutating preflights**, not package availability, actual execution or environment permission.
- The actual connected MCP-public catalog was enumerated completely in bounded pages: **206 public Abilities**: **68 `wp-ai-bridge`**, **74 `astra`**, **32 `gravityforms`**, **29 `rank-math`**, **3 `core`**. These are registered callable contracts, **not** 206 independently verified executable administrator tasks.
- The actual **indexed/public REST registry** was enumerated completely: **251 registered route patterns**, including **130 `wp/v2`** and **8 `wp-site-health/v1`**. Provider routes also exist under Rank Math, Code Snippets and others. Route presence, method and public argument schema are **not** permission or evidence of successful invocation.
- A legacy broad `site-context({})` call now returned a compact successful `current_user` with `projection.reason="catalog_limit"` and explicit `omitted_sections`, not a false empty collection or a `response_too_large` error. Select `current_user` or page named sections rather than expecting an unbounded inventory.
- Real named `site-context` pages for `plugins`, `external_abilities` and `taxonomies`, each with `limit=8`, completed successfully with `returned=8`, `has_more=true` and `next_offset=8`. The external Ability page truthfully reported `projection_truncated=true`; paging a shortened summary is not a lossless full-detail result.
- A named `extension-lifecycle` catalog lookup returned its exact input/output schemas; `rest-routes-read` and `rest-route-invoke` are both discoverable. A named, read-only registered REST lookup confirmed `/wp-site-health/v1/tests/background-updates` (GET), **without executing the health test**.
- Public Ability catalog text searches found **no** matching cron/schedule, WordPress Core upgrade, generic site backup/export, or SMTP operations. Across the **251 indexed REST routes**, there is **no identified generic WP-Cron event manager, WordPress Core upgrader, WXR site import/export or whole-site backup/restore contract**. The provider's `/rankmath/v1/status/runBackup` backs up **Rank Math settings**, not an entire WordPress site; Code Snippets import/export and `/wp-block-editor/v1/export` are likewise **feature-specific**, not WXR/site export. An absent public contract is not proof of a missing private wp-admin UI or a host service.

## Follow-up decisions (avoid duplicate features)

1. **Do not reopen #38, #46, #67 or #135.** Their valid published components remain available; manual ZIP dashboard staging is intentionally gone. Repeat live tests only when an operation is actually going to be used and current authorization is known.
2. **Use existing owners:** #119 for high-trust registered REST broader acceptance; #110 for bounded site-context/error provenance; #130 for truthful MCP/OAuth admin status; #126/#128 for Workspace; #134 for actual bidirectional file transfer. Gateway-specific parity and its file data plane remain [Gateway #130](https://github.com/AChWorks/mcp-gateway/issues/130) and [#147](https://github.com/AChWorks/mcp-gateway/issues/147). No Gateway code changes are implied by the Bridge audit.
3. **Accepted missing-workflow owners:** implement bounded **WP-Cron #138**, secure complete **WXR #139** and Bridge-accessible **native Site Health #140**; **Core Update #141** is strictly **read-only update availability detection** (reuse Site Health if sufficient, else add a minimal authorized status projection); executing a WordPress Core upgrade through Bridge is **not required or in scope**. Prioritize native contracts/provider reuse, exact access checks, tests and no duplicate PHP/SQL/filesystem/shell services. None of these features ships in v0.5.1.
4. **Role/CPT/taxonomy definitions remain provider-owned but achievable with custom code:** AI may author a purpose-built installed feature plugin or an authorized managed Code Snippet; WordPress registers CPT/taxonomy definitions on `init` and roles through appropriate lifecycle. The Bridge provides the available native snippet/source/extension operations with distinct elevated authorization, not a duplicate role/CPT framework or an unrestricted arbitrary-PHP executor. Full-site backup, SMTP/provider business logic and browser rendering remain with their natural providers/host/browser.
5. **Confidence boundary:** live catalog, version/grants, current native capability summary, lifecycle preflights, bounded site-context projection and indexed REST read are **observed**. Protected live mutations, interactive direct ChatGPT onboarding, actual generic REST operation on this site, private binary chat transfer, multisite Super Admin conditions and host-level backup/update operations were **not performed/proven**. Never use this matrix as a blanket “all Administrator operations succeeded” certificate.

## Practical client diagnosis

1. Read `wp-ai-bridge/bridge-info` to identify *installed* Bridge/Adapter versions and grants. Do not substitute GitHub's latest tag for the site's actual build.
2. Read `wp-ai-bridge/site-context` with `{"section":"current_user"}` for selected current native capability flags. On large sites, `{}` may return a truthful compact `projection` with omitted sections; use named paginated collections.
3. Use `wp-ai-bridge/abilities-read` (or the Gateway's exact named catalog tool) to inspect an exact Ability and public schema. The official MCP Adapter ordinarily exposes *generic* discover/inspect/execute tools; `tools/list` alone is not a complete list of underlying WordPress Abilities. Registered REST contracts have a separate `rest-routes-read` list/detail interface.
4. For plugin/theme mutations only, inspect the appropriate `wp-ai-bridge/extension-authorization` `{kind, action, install_source?}` preflight. Grant + capability + callback pass still returns `execution_permission:not_evaluated`; use actual Core operation only with current authorization and explicit intended effect.
5. Classify a miss by **specific source/WordPress capability, delegation, provider registration, version, source state, client transport and host**. Avoid assuming an unavailable provider operation is safe to recreate through direct wp-admin internals or a generic REST bypass.

This audit deliberately preserves the distinction between **source/CI implementation**, **real registry visibility**, **permission preflight**, and **actual completed operation**. The evidence is recoverable in [#99](https://github.com/AChWorks/wp-ai-bridge/issues/99) and the published v0.5.1 source; later installations must be rechecked rather than inheriting this site's permissions.
