# Large MCP payloads: WordPress content, blocks, and files

MCP clients should be able to administer large WordPress objects without passing entire pages or large binary files as one JSON tool response. The current Gateway source defaults to a finite 64 KiB ordinary response boundary and a separate bounded read-only tool budget (256 KiB by default); an installed Gateway version/configuration may differ. Raising either bound alone is not a reliable solution. WP AI Bridge uses the shared `Bounded_Payload` helper for JSON response budgeting and byte-exact UTF-8 text windows; the bound applies **per response**, not to the size of content WordPress can store.

## Distinguish total object size from per-message limits (Issue #134)

The source candidate replaces the old fixed 32 KiB serialized **MCP response** and 16 KiB **UTF-8 read window** caps with independently validated per-site administrator settings. Defaults are **128 KiB for encoded JSON** (administrator range 16–1024 KiB) and **128 KiB for the maximum requested UTF-8 text window** (range 4–512 KiB). These are **message/window** constraints, not hard limits on entire WordPress pages, long-form text or transferred files. WordPress content can be much larger when the original source permits it. An authenticated `content-read` can reconstruct a long body with source-hash-guarded windows, and the local regression exercises a body **larger than 1 MiB** end-to-end through this source-local API. Every continuation must preserve UTF-8 bytes and reject stale source identity; a full response or file is not automatically model-context-friendly.

**Configuration and effective wire sizes:** WordPress site administrators can adjust the four budgets under WP AI Bridge > Settings > MCP response and text budgets, through the native Settings API with a separate non-REST option from access grants. Invalid/out-of-range values keep the previous valid setting. Bridge projects the actual WordPress MCP Adapter 0.7 generic result representation: an encoded text content block **and** a separate structuredContent object, plus JSON-RPC safety headroom. Counting only the raw Ability JSON previously understated the final result and produced a measured **204,349-byte** MCP result for a nominal 128 KiB Bridge budget. The size-aware candidate now shrinks a text window until its conservatively projected Adapter envelope fits the administrator's per-response setting; Unicode escaping and the duplicated serialization both count. This is a Bridge/official Adapter envelope estimate, **not** proof that an older 64 KiB Gateway, HTTP proxy, or a particular external client can accept the response. A text window may shrink automatically to fit. The updated **128 KiB** response is intended for the next coordinated Bridge/Gateway delivery, not as proof that older installed Gateway versions accept it. An older Gateway with an observed **64 KiB ordinary decoded-response limit** may require the Bridge administrator to set the response budget to **48 KiB** until Gateway limits and actual wrapping overhead are updated/tested. Bridge never assumes the receiving client supports its chosen budget. Bridge cannot change external client/Gateway, PHP, hosting or proxy ceilings; align them independently and confirm with connected tests. These settings allocate no fixed capacity at rest: resource costs arise only when handling actual larger payloads. Aggregates are reconstructed by authorized source-bound continuations or an approved authenticated binary transport, not by unbounded JSON buffers.

**Input is not symmetric yet:** `content-upsert` currently accepts `content` only as one complete JSON string. A local WordPress call may store a large string, but this does *not* prove a ChatGPT/Gateway or other MCP host accepts that request. Large-text write/receipt needs an explicitly authorized, lossless and budgeted multi-request upload/streaming pathway (or an actual compatible text-file handoff), a target-native guarded commit and integrity verification. No generic text-file transport or partial WordPress write is shipped. Ordinary small typed edits should continue to use the current direct Ability without a staged file.

**Binary is a different plane:** `media-upload` currently decodes one complete Base64 JSON input with a **20 MiB default Bridge-side inline upload cap** (operator-adjustable up to the current PHP memory envelope in merged PR #145 (main source, not released)) further constrained by `wp_max_upload_size()`; many clients/paths can reject the JSON envelope *far earlier*. That ceiling is not an allowed aggregate cap for a future stream. `media-import-url` already streams only *safe accessible HTTP(S) source URLs* into the native Media Library under its own WordPress upload size cap; it does not ingest private chat files or send a WordPress file back to an external AI host. Workspace documents default to **512 KiB per record** (administrator range 64–1024 KiB) and task notes to **128 KiB per record** (range 16–256 KiB). These are separately validated private **Workspace record storage quotas**, not global text/file transfer maxima. Larger storage records do not make one-shot external client uploads of the same size automatically available.

For the required future two-way transfer, choose transport by **type and endpoint capability**, not by a global hardcoded file-size number: small typed JSON in normal Abilities; large UTF-8 in guarded windows for reads and verified multi-part/staged/streaming ingest for writes; binary through a common authenticated byte data plane; large structured collections through source-native pagination or complete verified exports. Each transfer has finite negotiated/per-site budgets, byte count/digest, source/destination identity and current authorization; unsupported modes must return clear `unsupported`/`too_large` **with the actual limiting layer and supported alternative** instead of silently truncating or widening authority.

Future acceptance in [#134](https://github.com/AChWorks/wp-ai-bridge/issues/134) explicitly covers both directions for empty, small, near-message-boundary, >1 MiB Unicode-rich text, opaque media/docs/archives and representative larger data (measured, not an arbitrary product cap). Record message vs aggregate sizes, host/PHP/Gateway limits, memory/temp disk/timeout and resource quotas; test hash equality, last-byte and UTF-8 boundaries, revoked grants, wrong principal/site and interrupted/uncertain results. **This source-level regression cannot stand in for actual external AI client file ingress/egress.** New public transport endpoints and access semantics need independent security/architecture approval; do not raise Gateway payload ceilings as a substitute for a real data plane.

## Type-aware data interchange (required direction, not all implemented)

Choose a transfer method from **content semantics, authority, recoverability and size**, not size alone. Keep the standard case a single bounded request; do not force every small result through a staged file.

| Data class | Appropriate contract | Current implementation / outstanding work |
| --- | --- | --- |
| Small JSON, configuration, metadata | Native structured result, exact target/schema, bounded output | Bridge typed Abilities and bounded registered-REST discovery plus guarded generic native invocation are **shipped in v0.5.1**; both REST grants default off and generic invocation is deliberately high-trust. Discovery was observed on the connected site; actual provider REST dispatch on production was not tested ([#119](https://github.com/AChWorks/wp-ai-bridge/issues/119)). |
| Long UTF-8 text, Gutenberg/HTML, Markdown or editable source | Exact object/revision/hash, UTF-8-safe byte windows or targeted subtree, continuation and completeness | Posts/revisions/blocks have dedicated bounded paths in current `main`; not a universal text endpoint. |
| Large structured lists/trees | Server-owned filters/projections/pagination, honest `has_more` and stable state when available | Ability catalog and site-context paging exist in `main`; provider-specific list semantics are not automatically pageable. |
| Media and opaque files (images, audio/video, PDF/archives) | MIME-aware preview/metadata plus authenticated binary streaming or provider-owned download/upload | Media upload and public-URL import exist; arbitrary large private binary ingress/egress is not generally implemented. |
| Executable plugin/theme ZIP | Lossless authorized transfer, distinct exact-package validation/review, and independent native installer consent | WordPress.org/public HTTPS installs work through `extension-lifecycle`; general external-client ZIP ingress/egress is not shipped (see #134). |
| Long-running or uncertain mutation | Stable operation/target ID, committed state or explicit `outcome_unknown`, truthful progress/completion | Current operations provide bounded failure/recovery semantics where implemented; there is no universal durable job/resume framework. |

Never fabricate supported cursor/range reads for a WordPress/provider API that does not supply stable source state; an opaque transfer handle is scoped and reauthorized, not a bypass capability. Preserve original encoding/bytes and distinguish MIME from merely display-friendly previews. Avoid silent value transformations, content leakage in broad discovery, or unverified claims that a write was rolled back.

## Gutenberg: discover, inspect, mutate

1. Call `wp-ai-bridge/blocks-find` with `post_id` and optional exact `block_name` (e.g. `core/button`, not `core/buttons`), `text_contains`, `class_name`, or `attribute_key` plus `attribute_value_contains`. Its flat matches contain canonical numeric `path`, optional `block_hash`, `hash_deferred`, direct-content summary, and the document's `content_hash` and `modified_gmt`. A block containing children defers its expensive recursive fingerprint by default; call `blocks-read(path)` to obtain the exact hash before a guarded write, or explicitly request `include_container_hash=true` when necessary. The finder does not expand or return the complete block tree.
2. If `complete=false`, resume using **`after_path=next_cursor`** and `expected_content_hash`. This cursor initializes traversal at the exact pre-order block path, avoiding any replay of earlier tree nodes. `limit` bounds matches and `scan_limit` bounds newly visited nodes; `walked` reports actual nodes visited by this scan. A batch can contain no matches and still have a continuation. `offset`/`next_offset` remain for compatibility, but offset-only continuations replay skipped nodes and are not recommended for very large pages. WordPress still loads/parses the *entire post content* on each request, so this is a traversal bound, not a constant-memory parsing guarantee. If the content hash changes, restart discovery.
3. Use `blocks-read` with `post_id`, `path`, `expected_content_hash`, `max_depth=0`, and optionally `include_attrs=false` for an attribute-heavy block. The resulting `block_hash` is compatible with the existing `blocks-mutate` stale-block guard. If discovery returned `hash_deferred=true`, read the selected parent first to obtain its exact subtree fingerprint. Increase `max_depth` only when descendants are needed (maximum 8).
4. Use the existing `blocks-mutate` with the returned document identity, block path, and block fingerprint. It returns the complete tree for small results, or `blocks=[]` plus `truncated=true` and the **committed** `content_hash` / `modified_gmt` for large results. The optional `response_mode=summary` requests the compact confirmation explicitly. There is no `response_mode=full` override for an oversized post-write response. Read the edited path again if further block detail is required.

Legacy `blocks-read(post_id)` remains available for small pages. For an oversized result it returns `blocks_response_too_large` with the supported find/targeted-read alternative instead of handing an unbounded result to Gateway. A large block's individual attribute data can also exceed the response budget; request `include_attrs=false` for its bounded fingerprint/summary.

## Raw Gutenberg markup or other large post content

`content-read(action=get,id=...)` returns the usual full `content` for small objects. For large objects it returns metadata, `content_hash`, `content_total_bytes`, `content_next_offset=0`, and `content_complete=false`, without dumping the entire body.

Read the exact text with `content_offset` (byte offset; start at zero), optional `content_max_bytes` (maximum given by current site setting; default 131072 bytes), and `expected_content_hash` for continuation. Every response supplies `content`, `content_next_offset`, `content_total_bytes`, and `content_complete`. Continue until complete. All chunks are UTF-8 safe, join to the exact original bytes, and are tied to the immutable document content hash. The Bridge reduces a requested window when the actual JSON-escaped representation would otherwise overflow.

For list requests with `include_content=true`, a large item may omit its inline body with `content_complete=false`; retrieve that item through `action=get` with windows. If list metadata is too large, Bridge uses a fixed-size compact projection rather than returning unbounded titles/excerpts; reduce `per_page` if a many-item result still exceeds the envelope. A write/restore acknowledgment identifies the **committed** content/state hashes even when full metadata and body cannot be returned.

**Large title/excerpt or other metadata:** When an individual response cannot fit even after shrinking the body, the item returns `projection_truncated=true` and `omitted_fields` with fixed committed identity (`id`, `post_type`, `modified_gmt`, `content_hash`, `state_hash`). Recover each omitted text value with `content-read(action=get,id=...,text_field=title|excerpt|slug|status|template,text_offset=0,text_max_bytes=...,expected_state_hash=...)`, then repeat using `text_offset=text_next_offset` until `text_complete=true`. `text_hash` permits byte-exact reassembly; the state hash guards continuations against an intervening metadata edit. A successful mutation must not be reported as a response-size error merely because its title or excerpt is very large.

## Historical revisions: bounded discovery and exact selected reads

`revisions-read` retains its **array** result and existing small-revision behavior. Request `post_id` and optional `limit` (1-50), `offset` (nonnegative, at most 100000), and `include_content`. A list normally includes the original revision metadata; if an item or aggregate exceeds the encoded-response budget, it returns a compact identity with `projection_truncated=true`, `omitted_fields`, `id`, `parent_id`, `content_hash`, `content_total_bytes`, and hashes/byte counts for title and excerpt. For `include_content=true`, a large body is omitted and clearly marked; the operation never returns an unbounded historical body or silently discards revision IDs. Decrease `limit` if the compact aggregate still exceeds the budget. Offset-based discovery is not a snapshot while new revisions are written; always select a stable revision ID before reconstruction.

Choose an exact revision with `post_id` + `revision_id`. The result is still a **single-element array**, preserving the existing output shape. For full content, set `include_content=true`, `content_offset=0` and optional `content_max_bytes` (4 through the current site text-window limit); take `content_hash` and `content_next_offset` from the returned element, and continue with the same parent and revision IDs, `content_offset=content_next_offset` and `expected_content_hash=content_hash` until `content_complete=true`. Offsets count UTF-8 **bytes**, not characters. Concatenate chunks exactly; `content_total_bytes` and SHA-256 `content_hash` verify reconstruction. Incorrect boundaries, missing continuation identity, changes to the selected revision and mismatched parent IDs fail explicitly.

A large revision title or excerpt is not silently truncated: use the same `post_id` + `revision_id`, `text_field=title|excerpt`, `text_offset=0` and optional `text_max_bytes` (4 through the current site text-window limit); continue with `text_offset=text_next_offset` and `expected_text_hash=text_hash` until `text_complete=true`. The exact text hashes and lengths allow independent reconstruction. The selected revision is reloaded and its `post_parent` association, Site Read grant and current principal's WordPress `edit_post` capability (as in Core's revision controller) are checked **on every continuation**. `revision-restore` is **not** implied by reading a revision and still requires separate Builder Write/edit authority and its existing stale-write guards.

These semantics are tracked by [Issue #105](https://github.com/AChWorks/wp-ai-bridge/issues/105). They describe the source contract containing this change, not evidence that older deployed plugin versions already support it. Do not increase Gateway response limits or move raw revision bodies into MCP arguments.

## Binary media and executable packages are different

Binary files must not be treated as giant text values merely to pass through MCP JSON. Use WordPress-authorized and streaming transfer paths:
- `media-import-url` already downloads eligible external HTTP(S) sources with bounded streaming into native Media Library storage.
- The existing `media-upload` base64 Ability is for appropriately sized inline MCP payloads; it is **not** a scalable transport for arbitrarily large files.
- Administrator-authorized plugin/theme install from a reviewed public HTTPS package uses `extension-lifecycle` and native Core Upgrader handling. A locally generated or user-provided archive requires a genuine client-to-WordPress binary transfer mechanism before installation can even be considered; bidirectional exchange is tracked by [#134](https://github.com/AChWorks/wp-ai-bridge/issues/134). The transfer itself must never install or activate code.

Bidirectional client file exchange needs verified send **and** receive handshakes, purpose-specific access in each direction, finite streaming/chunks or another approved artifact transport, bounded storage, hash/length integrity, expiry/cleanup/recovery, and native WordPress media or extension authority. Do not reassemble huge base64 files in ordinary MCP tool arguments, expose arbitrary filesystem paths, or relax Gateway decoded response limits. Gateway [#122](https://github.com/AChWorks/mcp-gateway/issues/122) completed its bounded-result/error slice and documented future file-transfer semantics, but did **not** ship a general WordPress private binary transport.

## Main-integrated inline binary file egress (Issue #134 / merged PR #145; not released)

Implemented in main by merged PR #145, not yet in a published release: **wp-ai-bridge/file-bytes-read**. The caller uses action=inspect, source_type=media and the exact attachment source_id. Bridge first checks current Site Read grant plus native read_post, verifies the real file remains inside the canonical current-blog WordPress uploads root, and returns a SHA-256 digest plus an opaque HMAC snapshot bound to the source, WordPress principal/blog and authenticated client identity. No server-local path or public signed URL is returned.

For action=chunk, the caller supplies the same media source, offset, max_bytes, expected_snapshot and expected_sha256. Every read rechecks WordPress permissions and filesystem identity, returns lossless Base64 with exact continuation offsets, and bounds the actual dual-encoded MCP response to the configured response_kib. The final window re-hashes the original file; clients MUST verify full reconstructed SHA-256, as same-size filesystem changes between requests may escape second-level mtime/ctime checks. This is a best-effort read snapshot, not an immutable private copy; stale or mismatched transfers fail closed when detected.

The new independently configurable inline_file_read_mib option defaults to 128 MiB (operator upper bound derived from PHP integer/file handling) and applies ONLY to this inline JSON/Base64 fallback. It does NOT cap WordPress file/object storage, other binary transports or future streaming. Binary response windows and whole-file capacity must never be conflated. Large-file Base64 incurs request/wire overhead; provider-supported secure streaming or private receipts would need separate authorization and proof.

Existing media-upload remains a separate, one-request Base64 Media Library ingress under native upload permissions. Its formerly fixed 20 MiB Bridge fallback budget is now per-site operator-configurable through inline_media_upload_mib (20 MiB default, operator maximum derived from PHP memory), still restricted by WordPress wp_max_upload_size (upload_max_filesize / post_max_size), provider authorization and client/Gateway request body limits. This is NOT a maximum aggregate file size for future streaming. This one-request inline fallback does not itself solve durable chunked private ingress, native WXR import, hosted-client attachment delivery or Gateway interoperability; separate v0.6.0 private-transfer/WXR Abilities supply the WordPress-side source functions. The file-bytes-read Ability is integrated into main by merged PR #145, but not published in v0.5.1; hosted ChatGPT attachment reception, Gateway forwarding and production proof remain separate.

## Public authenticated private multipart lifecycle (Issue #134 / PR #145; not shipped)

The merged main source exposes **`wp-ai-bridge/private-transfer` as a public, authenticated native WordPress MCP Ability** using the existing Bridge OAuth endpoint, not as a public file URL or a direct filesystem API. `Private_Transfer_Session` is the internal PHP storage implementation behind that purpose-scoped Ability and the separate Media/text consumers. Each transfer binds a random opaque ID to the current blog, WordPress principal and authenticated OAuth client; continuations reauthorize and enforce independent finite operator settings. Remote clients can `limits/begin/append/status/verify/read/cancel/release` as permitted by their purpose and state. Only a current-blog `manage_options` OAuth administrator can use `admin_release` for an unknown irreversible effect, without receiving the original source bytes or file path.

Staging a private Media, text or WXR object does **not** automatically import, edit, install, extract, execute, publish or create a downloadable ChatGPT attachment. The separate explicitly permission-checked `transfer-media-import` and `transfer-content-commit` Abilities perform effectful native WordPress operations with one-way claim fencing. `transfer-media-export` creates a persisted private copy and reserves resources, so it is classified **readonly=false, destructive=false, idempotent=false**, even though the source Media attachment itself is only read. Internal-only `verified_private_source` is never a public tool result. The main-integrated source verifies a file's full SHA-256 before consumption, returns bounded windows and retains monotonic effect identity to prevent blind retries.

Current boundaries: no external ChatGPT-host attachment upload/download proof, no Gateway-specific binary data-plane handoff, no multi-host/shared-storage guarantee, no hosted ChatGPT/Gateway WXR attachment roundtrip (the main-integrated native direct loopback OAuth/MCP WXR roundtrip is proven), and no production release proof. The private staging directory remains outside the WordPress webroot, with per-site lazy cleanup instead of a daemon. The native effect fence is durably published with a file fsync and a post-rename *directory* fsync; where that directory operation is unsupported, irreversible effects fail closed. The #145 source passed the required independent security review and exact-HEAD CI before merging; external host/Gateway acceptance and release obligations remain open under #134.

## WXR private import/export on the shared byte plane (Issue #139; introduced in v0.6.0 source)

The v0.6.0 source registers `wxr-export-create` (native Core WXR XML to expiring private `wxr_read` lease) and `wxr-import-preview` (verified inbound `purpose=wxr` structural-only scanner). To use the official WordPress Importer **without duplicating its business logic**, the new `wxr-import-plan` checks the active reviewed upstream WordPress Importer 0.9.6 loaded with `WP_LOAD_IMPORTERS` set **before request bootstrap**; it issues a MAC-bound, source/author/conflict/target/authorization-specific preview token. The separate `wxr-import-execute` requires that exact token and an explicit confirmation. The constrained official Importer subclass consumes only exactly the validated primitive/array serialized metadata, never the upstream class-name rewrite over encoded string contents, and denies PHP class materialization. Non-no-op O:-looking literal strings must survive byte-for-byte. Its verified lease becomes durably and irreversibly claimed before calling the official Importer's native method. WordPress creates no new users and makes no remote media fetches on this path; public/published content and existing-content effects require additional Live Content authorization. The private transfer status exposes its one-way effect outcome; a timeout, non-atomic partial import or unknown result must be inspected, not repeated. Unsupported/missing provider, mismatched CPT/taxonomy, unsafe serialized object metadata, permission revocation or WXR byte drift fail closed. **Do not confuse successful native WordPress and loopback HTTPS/OAuth/MCP imports with hosted ChatGPT/Gateway file attachment transfer, production release, or a full WXR site backup.**

## Direct Bridge versus MCP Gateway

The direct WordPress client and the Gateway route must preserve the *same source identity, hash, MIME/encoding, completeness and execution outcome*. A new bounded JSON Bridge Ability can normally use Gateway's existing catalog and Ability execution path after authorization. **Exception:** an Ability that dynamically selects REST routes/methods cannot inherit readonly classification from a static tool annotation. The current Gateway WordPress connector uses static Ability metadata for its read/mutate/destructive permission classes; until a separate per-operation classification is verified, this generic executor requires explicit elevated/unclassified Gateway authorization. **General authenticated, private binary file handoff** does **not** fit the current Gateway JSON-only `wordpress-ability-execute` contract by itself; an existing **small inline** Bridge `media-upload` Base64 call is a different, size-bounded operation, not proof of transferring a ZIP/PDF/office attachment from an AI client or sending a WordPress file to the model. Complete file exchange requires an authenticated streaming/multipart handoff, a supported scoped direct-to-Bridge transfer, or an equivalent **verified** client workflow. Plan an interoperable, Target/user/client-bound contract with [Gateway remote I/O design](https://github.com/AChWorks/mcp-gateway/blob/main/docs/REMOTE-IO-CONTRACT.md); record WordPress Ability-routing parity issues under [mcp-gateway#130](https://github.com/AChWorks/mcp-gateway/issues/130), **real brokered client-to-Target and Target-to-client file handoff** under [mcp-gateway#147](https://github.com/AChWorks/mcp-gateway/issues/147), **measured format/size/client compatibility** under [mcp-gateway#154](https://github.com/AChWorks/mcp-gateway/issues/154), and **Gateway Owner Admin operational tuning** under [mcp-gateway#153](https://github.com/AChWorks/mcp-gateway/issues/153). Those repository owners control their own code and decisions; this Bridge document does not authorize a Gateway mutation. Do not imply that every AI client can upload files through MCP resources or that an accepted data-plane design is already operational.

For future MCP protocol features, negotiate actual Adapter/client versions rather than assuming a newer specification, resource-link support or asynchronous task support is present. Existing tested ChatGPT and Gateway OAuth/MCP operation must continue to function until separately reviewed replacement/upgrade paths are accepted.

### Native private effect recovery (merged PR #145; not released)

The one-way native `.claim` is written into an owner-only unpublished temporary and atomically published **only after complete flush**, under the stable per-lease lock. A process dying before publication leaves an inert pending file; an existing final claim is never deleted to permit replay. Published/legacy incomplete claims remain fenced as `committing`/unknown. Stale unpublished pending files are reconciled only when their session is not locked. The dual-generation `.meta` journal remains the source of truth for reservations and crash-resumable offsets.

`private-transfer(action=admin_release, transfer_id, acknowledge_unknown=true)` is a **separate narrow management action** requiring authenticated MCP OAuth and the current blog's WordPress `manage_options`, even when the original Editor's Builder Write grant was revoked. It can only release the private bytes/reservation for an exact `committing`/unknown claim. It cannot read, append, cancel, retry, verify, change ownership, or delete the immutable claim fence; the response omits the originating principal's content digest and byte count. Inspect the actual WordPress destination **before** acknowledging uncertainty; byte release cannot undo a native effect.

Unrelated admissions inspect atomically published, conservative reservation generations non-blockingly while one Media sideload holds its own per-lease lock through Core image processing; the global admission guard never waits on that long-running lock. If a busy reservation cannot be safely classified, admission fails promptly without relaxing capacity or confidentiality. Cancellation of the active lease is refused while the native Media operation holds it. Source-level review and integration are complete, but real hosted-client and production acceptance remain separate gates before publication.

## Contract ownership and development sequence

The **Bridge** owns independently usable **direct WordPress** data exchange and its own administrator-controlled response/window/Workspace storage limits. [Bridge #134](https://github.com/AChWorks/wp-ai-bridge/issues/134) is the pending inbound large UTF-8 and authenticated **two-way** private binary/file transport outcome. Keep normal small typed Abilities cheap. Do not invent a hard aggregate file maximum from a JSON limit, a 16 KiB SFTP inline call, a Workspace record quota, or the WordPress single-request Media cap. A passive ZIP/other archive receipt never automatically installs, extracts or executes it.

The **Gateway**, if used, owns only its own client-neutral brokered handoff ([#147](https://github.com/AChWorks/mcp-gateway/issues/147)), native SSH data-plane adapters ([#123](https://github.com/AChWorks/mcp-gateway/issues/123)), operational settings ([#153](https://github.com/AChWorks/mcp-gateway/issues/153)) and cross-project observed size/format/client matrix ([#154](https://github.com/AChWorks/mcp-gateway/issues/154)). **Direct Bridge implementation must not wait on Gateway architecture** and Bridge changes never implicitly authorize Gateway code edits. Source integration or a test fixture is not proof that the installed ChatGPT/other client can send or receive attachments. Keep each source/release/installed-runtime result explicit.

Within WordPress, [WXR #139](https://github.com/AChWorks/wp-ai-bridge/issues/139) owns native Core export and official importer behavior; its independently reviewed native implementation is main-integrated through PR #146, separately from #134 hosted-client delivery. Hosted-model attachment materialization remains unverified under #134 despite successful native and loopback OAuth/MCP byte-window WXR exchange. [Cron #138](https://github.com/AChWorks/wp-ai-bridge/issues/138) is an independent high-risk native event workflow, and [Site Health #140](https://github.com/AChWorks/wp-ai-bridge/issues/140) / [read-only Core update status #141](https://github.com/AChWorks/wp-ai-bridge/issues/141) need authenticated live acceptance, **not duplicate source implementations**.

**Current integrated sequence:** PR #145 delivers the shared private-byte transport and PR #146 delivers independently reviewed Core WXR export, verified ingress/preview, consent-bound official native Importer execution, durable no-replay recovery and direct loopback HTTPS/OAuth/MCP acceptance in `main`. Both source outcomes first enter the v0.6.0 candidate, not v0.5.1. Remaining delivery evidence must be separately established for a release/production installation, hosted ChatGPT/other-client attachment materialization, Gateway forwarding, remote public networks and multi-host private storage; Cron #138 has its own separate review. Merged source is not a published or production capability.

## Reusing this pattern elsewhere

For every potentially large read/result:
- discover/list cheaply and target by stable WordPress identity;
- include a content/version hash, bounded continuation, and an explicit completeness indicator;
- budget **serialized JSON bytes**, including Unicode escapes and protocol headroom;
- never return ambiguous failure after persistence only because full readback is too large;
- reuse WordPress/provider capabilities and preserve per-object authority on each continuation;
- route actual binary blobs through the owning media/extension API, not a general filesystem or PHP/SQL endpoint.

The shared `WP_AI_Bridge\Support\Bounded_Payload` handles the encoded result budget and UTF-8 content windows. Each owning Ability retains its own authorization and query semantics.


## Main-integrated reusable private byte ingestion (Issue #134 / merged PR #145; NOT SHIPPED)

Owner accepted a generic, client-neutral session lifecycle on the **existing** authenticated Bridge OAuth MCP endpoint. Main-integrated `wp-ai-bridge/private-transfer` operations: limits, begin, append, status, verify, cancel, snapshot-only read and effect-receipt-preserving release. Begin supplies purpose (media, text, or wxr), total byte length and SHA-256. The server returns an opaque lease tied to the current blog, WordPress principal and authenticated OAuth client plus the effective raw chunk, request, file, aggregate reservation, active session and lease limits. Append accepts a Base64 chunk with an exact offset; identical replay is safe, a gap or differing replay fails. Verify checks full source length and SHA-256; cancel verifies private cleanup. Staging is **inert**: no public temporary URL, no PHP/file path read, no import/installation/activation/post update, and no assumption that a client sees a model-downloadable attachment.

A separate WordPress administrator form persists six independent wp_ai_bridge_transfer_limits values in WordPress Options, independently of grants and legacy inline payload settings. Defaults (subject to actual host limits): 128 KiB incoming MCP message, 48 KiB raw chunk, 256 MiB one staged file, 1024 MiB aggregate active reservation, 8 live leases and 180 minutes per lease. These are **administrator-adjustable resource reservations, NOT built-in file-type limits**; their validated numerical maxima derive from current PHP memory and integer ranges. Dynamic private disk checks can reject reservations with an actionable transfer_disk_insufficient, even when a larger number is configured. Neither Bridge nor WordPress can override the actual PHP, disk, HTTP, Gateway, proxy or client boundaries. Increasing one setting does not change those external limits. Chunking prevents the aggregate file from inheriting the per-MCP message ceiling. The operator must provide durable shared private storage/sticky routing before multi-host resume can be promised.
