# Source-agnostic private ZIP packages — Issue #108

This describes a source implementation integrated through [PR #122](https://github.com/AChWorks/wp-ai-bridge/pull/122), **not** a published release or deployed-site capability. Installing plugin/theme code is an administrator-trust operation, not a sandbox.

## Bytes transport and ownership

**Production transport requirement:** this Bridge-owned browser upload and its admin page fail closed unless WordPress recognizes HTTPS via is_ssl(). Use real HTTPS for credentials and private ZIP bytes. When TLS terminates at a trusted reverse proxy, configure the WordPress server's HTTPS environment from that trusted proxy (as described by WordPress reverse-proxy documentation); do not trust arbitrary client-supplied forwarded-protocol headers. Plain HTTP upload is not supported, including loopback-only development; tests use an isolated real self-signed HTTPS server.

In the WordPress dashboard, **WP AI Bridge → Private ZIP Packages** uploads a plugin or theme ZIP through Bridge's own logged-in, nonce-checked admin-post action. The archive can originate from an AI, human, vendor or developer; its origin never substitutes for authorization. Files are staged outside the public web root and are **not installed** at upload time. Neither a public download URL nor an AI-controlled local file path is required.

The uploading administrator selects a currently approved OAuth client. The staged artifact is bound to the exact WordPress user, site/blog and selected client ID plus approval revision. Revoking an extra client approval invalidates its staged artifacts. The approved, authenticated MCP client can then use:

- `wp-ai-bridge/private-packages-read` — `{"action":"list"}` or `{"action":"get","artifact_id":"..."}` — to see bounded, path-free metadata and exact SHA-256;
- `wp-ai-bridge/private-package-install` — explicit `artifact_id`, `kind` and `sha256` — to hand only the exact reviewed artifact to native WordPress Core Upgrader for installation, **never activation**.

The old `extension-lifecycle` WordPress.org slug and safe public HTTPS source paths remain unchanged.

**Transport limitation:** ChatGPT/MCP Adapter and the current Gateway typed JSON Ability model are not assumed to support ZIP bytes or multipart attachments. Browser multipart upload is a supported **Bridge-owned transfer path**, not a wp-admin-only installation workaround. Gateway attachment streaming needs a separately verified client/Target-scoped handoff contract coordinated by Gateway #130; no cross-repository compatibility is claimed here.

## Authorization and bounded validation

Both default-off **Code & Extensions** and **External Packages** grants, `manage_options`, and the kind-specific native `install_plugins` / `install_themes` capability are required. `DISALLOW_FILE_MODS` denies staging/installation. The admin browser upload requires a WordPress login session and CSRF nonce. AI Ability calls additionally require the currently validated OAuth/MCP client context; there is no caller-supplied client ID, bearer upload route, arbitrary filesystem path or raw byte argument.

- Private directory: server-owned, mode 0700, outside web roots; ZIP files are mode 0600 and identified by random 48-character hex IDs.
- **Durable storage-domain identity:** before any ZIP bytes are staged, the Bridge binds the current blog to one random storage-domain identity persisted as a non-sensitive WordPress option and an exact matching 0600 marker in its 0700 private staging directory. Every web/PHP-FPM, scheduled cron and WP-CLI worker that installs, expires, deactivates or uninstalls private ZIPs must use the **same physically shared private staging volume** with the same marker; a matching pathname or database alone is not proof of shared storage. If the executing PHP SAPI/container has a different sys_get_temp_dir() or a separate mount, the Bridge fails closed, retaining original ZIP bytes, metadata, claims and scheduled cleanup rather than pretending successful retirement. Grant filesystem access to authorized cleanup operators, especially WP-CLI when upload bytes are 0600. For cross-host sites, use an explicitly shared lock-coherent private volume and a compatible routing/storage configuration; sticky web routing alone does NOT make CLI/uninstall cleanup safe.
- Maximum compressed ZIP length: 64 MiB and no higher than `wp_max_upload_size()`. Max total uncompressed entries: 256 MiB and 4096 entries, with per-entry size, expansion ratio, file/directory-collision and path limits.
- Structural review: PHP ZipArchive required; deny path traversal, symlinks/special types, duplicate/colliding entries, inconsistent roots, unreadable/encrypted entries, absent plugin/theme headers, and invalid theme layouts; WordPress Core remains the package validation authority.
- Staging: 1-hour TTL, at most 4 open records per user and 24 per blog; a bounded per-blog MySQL/MariaDB advisory lock serializes quota allocation across concurrent WordPress workers and fails closed if unavailable. WordPress cron retires expired files and bounded outcome records, but only after acquiring the same shared extension mutation coordinator; a busy lock defers cleanup instead of touching in-use ZIP bytes.

**Multi-node deployment boundary:** database-wide quota locking alone is insufficient. Every lifecycle actor must access the **same physical private staging volume and marker**; sticky routing or identical `/tmp` paths across distinct volumes does not satisfy this requirement. The separate shared `WP_CONTENT_DIR` filesystem lock must also coordinate extension mutation across workers. Unsupported topologies fail closed; generic distributed file-storage compatibility is not claimed.

AI-visible responses contain metadata only. They never contain uploaded bytes, token values or local paths. Successful Core installs and recovery-required outcomes also produce bounded, credential-free entries in the existing Bridge mutation log. A failed audit-option write after native installation is reported as recovery-required and retains the once-only installation claim; no automatic retry. If pre-Core state persistence fails AND the private ZIP cannot be deleted, the bounded inspection metadata includes cleanup_required=true (never the filesystem path); the existing one-way claim prevents replay, and subsequent normal cron cleanup retries byte retirement and clears that flag only after removal is verified.

## Deactivation and uninstall

The same WordPress-installation-wide native extension lock also protects ongoing browser staging and deactivation/uninstall cleanup; if an installation is in progress, cleanup fails closed instead of deleting a ZIP while Core is consuming it. Deactivating the Bridge retires every Bridge-owned staged ZIP and orphan ZIP and unschedules its cleanup event, including every blog on network-wide multisite deactivation. The lifecycle validates the persisted per-blog domain identity against the original directory marker BEFORE touching ZIPs, metadata, claims or cron; a missing/mismatched storage domain aborts the deactivation/uninstall. When the correctly shared root is accessible, the Bridge confirms ZIP removal, retires disposable metadata/claims and cron, then removes the inert marker and durable domain identity. Existing private ZIPs from an older/unbound staging implementation cannot be silently treated as absent; operators must reconcile any legacy artifacts before relying on this lifecycle. Uninstall performs the same strict cleanup **before** removing ordinary Bridge options; a storage failure blocks uninstall rather than silently leaving private executable bytes. Disposable ZIP metadata and claims are removed. For installs that might have begun or returned an uncertain Core outcome, only a minimal non-executable recovery tombstone and one-way claim are deliberately preserved so a subsequent reinstallation cannot blindly replay an unknown install. These records contain no executable ZIP bytes or private filesystem paths. Reconcile the real installed extension with WordPress Core before any new install; uninstall is not an automatic rollback.

## Installation, recovery and release boundary

A WordPress-installation-wide **two-layer coordinator** serializes all Bridge-owned plugin/theme Core install pathways, including WordPress.org, public HTTPS ZIP, and private ZIP requests across multisite blogs. Its canonical order is **non-blocking exclusive PHP flock on one empty, stable, non-executable file in the shared WP_CONTENT_DIR**, followed by a non-blocking MySQL/MariaDB named lock. The file descriptor remains open through all native filesystem effects, state persistence, and cleanup. Losing/replacing the ordinary WordPress database connection cannot release that process-owned exclusion while PHP is still running; the later DB ownership recheck conservatively reports a recovery-required outcome. Both layers are released in reverse order and OS file locking is retired automatically if the worker terminates. If either lock cannot be acquired, the operation fails before an irreversible claim or Core mutation. **Supported deployments must place the relevant shared plugin/theme mutation directories and this inert lock file on the same consistently accessible lock-coherent WP_CONTENT_DIR filesystem (or guarantee equivalent cross-worker filesystem lock coordination).** Non-coherent network filesystems, separate per-node lock file copies, and non-Bridge extension writers are outside the claimed safety envelope; do not enable private package installation on unsupported storage. Contention fails before private-archive claim/irreversible effects, and native-install ordinary success requires the final DB ownership check. Independent administrators or unrelated plugins changing files outside this coordinator remain a documented operational concurrency limit.

Immediately before executing Core, the Bridge rechecks the user/site/client identity, current approval, all grants/native capabilities, SHA-256/byte length and archive structure. A once-only, atomic option insertion claims the exact artifact, denying concurrent/replayed installation. After the Core boundary, any ambiguous result, lost database ownership, failed durable artifact-state transition, audit persistence failure or cleanup problem returns a bounded recovery-required error, retains the claim, and prohibits blind retry. The pre-Core installing state is also verified before invoking the native Upgrader; inability to persist it retires the staged ZIP without executing the package. Installation is never automatic activation.
