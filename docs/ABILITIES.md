# Ability reference

Bridge-owned Ability names use the `wp-ai-bridge/` namespace.

The baseline installation registers the core Bridge surfaces below. Optional Gravity Forms and Code Snippets fallbacks are registered only when their supported provider APIs are available. Astra and other suitable provider Abilities are reused rather than duplicated. **This reference follows current maintained source; a deployed release may be older.** For an actual site, check its `bridge-info` plugin version and then discover available Abilities through its authenticated MCP Adapter/Gateway route. Listing an Ability does not establish executable WordPress/provider permission.

### Exact private Workspace deletion and safe recovery (#126)

`wp-ai-bridge/workspace-delete` accepts **exactly** `kind` (`document` or `task`), positive `id`, current `blog_id`, nonempty exact `project_ref`, `expected_version`, `expected_state_hash`, and the literal confirmation `PERMANENTLY DELETE DOCUMENT <id>` or `PERMANENTLY DELETE TASK <id>`. It requires an OAuth-authenticated MCP client, the current site administrator, WordPress `delete_post`, enabled Builder Write and Users & Destructive groups. It cannot delete unbound/legacy records, general posts, foreign blog records, or any unspecified collection. It first establishes a site-local admission lock and a metadata-CAS deletion fence, then force-deletes the one private CPT post. Success is returned **only after verifying the record and its private state metadata no longer exist**. A stale state fails without deletion. A `pre_delete_post` enforcement guard rechecks exact blog/table, private record/fence, DB lock and current destructive grant after earlier hooks, then rechecks again at the native `before_delete_post` boundary. Both guards check that their exact callback is terminal within the PHP_INT_MAX priority bucket, including callbacks dynamically appended during hook execution; if another callback is scheduled after the guard, the operation is interrupted before WordPress cleanup rather than trusting PHP_INT_MAX to be inherently final. WordPress's `WP_Hook` dispatcher does not finally-unwind when callbacks throw. The destructive Ability therefore uses a **shared exception-safe hook boundary** for its permission callback, repeated authorization and pre-native metadata/CAS, guarded native `wp_delete_post()`, conditional compensation, and best-effort Activity. On a callback exception it verifies the pre-operation global hook stack and rebuilds the affected named `WP_Hook` dispatchers plus the otherwise hidden universal `all` dispatcher using **public registration APIs**, preserving every provider callback ID, priority, accepted argument count and order; only after fully proven recovery may an error be re-thrown, a conservative `workspace_delete_outcome_unknown` reported, or a verified deletion receipt preserved after Activity failure. Native and compensation snapshots participate in the same tracked scope lifecycle as permission and execute callbacks, so a verified inner reconstruction of `all` rebases every still-live enclosing snapshot without accepting unverified third-party replacements. An already-active outer universal `all` dispatcher is never replaced; native deletion is refused under that condition. WordPress 7.1+ may normalize a thrown Ability callback exception into `ability_callback_exception` or `ability_invalid_permissions` and continue the request, so propagation alone is **not** a recovery strategy. **If exact dispatcher recovery cannot be proven, the Bridge first replaces the WordPress hook registry with callback-free terminal state and clears the global hook stack, then terminates normal PHP execution with HTTP 500 (CLI exit code 70).** PHP `exit()` still invokes registered PHP shutdown functions, including WordPress's own shutdown handler; quarantine prevents previously registered WordPress `shutdown`/`all` callbacks from being dispatched through that registry. Independent PHP shutdown functions are outside WordPress's hook framework and are not suppressed. The Bridge cannot return a normal `WP_Error` or allow WordPress Ability execution to resume with inconsistent hook state. Exact Bridge-owned native sentinel exceptions alone qualify for verified pre-native CAS compensation or conservative native ambiguity, while unrelated provider exceptions retain their provider-error identity after safe dispatcher recovery. Nested deletion into an already-active native delete hook is denied pre-native. A pre-native interruption permits only the verified CAS compensation; an interruption after `before_delete_post` has started remains `workspace_delete_outcome_unknown`. If WordPress conclusively vetoes before native deletion starts, the exact CAS fence is conditionally restored under lock and `workspace_delete_vetoed` reports the unchanged record. A Bridge-denied post-CAS/pre-native attempt is likewise conditionally restored under verified admission with `workspace_delete_aborted`; this is not a successful delete. An uncertain or partial native effect still returns `workspace_delete_outcome_unknown`, blocks subsequent store edits, and requires operator reconciliation rather than blind retries. The canonical document-key claim is **intentionally retained** after deletion; a deleted project's `key` cannot be silently reused. Do not use `Store::clear()` for fixture cleanup. Public destructive API adoption, live-site use, and release require owner approval and separate high-assurance security review.

### WP-Cron inventory and provider-owned lifecycle (Issue #138; available from v0.6.3)

Published v0.6.3+ includes `wp-ai-bridge/cron-events-read` under the existing default-off **Site Configuration** grant and native administrator authority; multisite requires network-administrator authority. `action=list` returns up to 25 entries with an opaque site-bound `event_id`, hook (explicitly `hook_truncated` if needed), next run UTC/timestamp, recurrence/interval (with `recurrence_truncated` where necessary), argument **count only**, callback registration observation and overdue flag. It never returns serialized arguments, sensitive callback state, or provider input. `action=get` selects a present event by opaque identity. Empty or missing Cron data does not invent executions.

Every inventory response carries a snapshot digest. Pass `expected_snapshot` with the next `offset` to detect a changed native Cron option and restart instead of silently mixing pages. Exact `hook` filtering is optional. The native WordPress scheduler stores all events in one site-scoped option, so inspection must read that Core representation: Bridge scans it with proportional CPU time but retains only the selected page and incremental snapshot state. There is no arbitrary 4,096-event count refusal; real WordPress memory needed to load the original Cron option is **not** constant, and representative large-site measurements remain required. Malformed or unrepresentable native data is refused instead of silently omitted. `wordpress_cron_disabled` only reports the local constant; `external_trigger_verified:false` deliberately makes **no** inference about an OS cron job or whether any callback ran. A registered callback does not certify that a provider job is safe to execute manually.

**Published native lifecycle (v0.6.3+):** a separate `wp-ai-bridge/cron-events-manage` Ability now supports `profiles` discovery and **provider-authorized exact one-off/recurring schedule, reschedule and unschedule**. An installed trusted provider must opt in through the WordPress `wp_ai_bridge_cron_profiles` filter: it registers immutable callback hook + arguments + permitted lifecycle actions. The remote MCP caller supplies only a profile ID and UTC timestamp/registered recurrence, never PHP code, callbacks or event arguments. Discover many authorized profiles through `action=profiles` with optional `offset` (default 0) and `limit` (default 10, maximum 50 per request); results include `profile_total`, `profile_next_offset`, `profile_has_more` and a source-bound `snapshot`. Resume with `expected_snapshot` to fail closed if installed provider registrations change. The returned page shrinks to fit a conservative 16 KiB projected MCP envelope when the optional shared payload-budget component is not installed; if that separately reviewed component is present, its administrator-configured response budget applies instead. This does **not** impose a cap on the total registered profile count or leak immutable provider arguments.

All modifications require default-off **Site Configuration**, native `manage_options` (on multisite also `manage_network_options`), the provider profile's explicit action permission, a valid future UTC time, an existing registered callback and the current reader's exact full-inventory `expected_snapshot`. Reschedule/cancel also require the reader's opaque `event_id`. Bridge serializes its own Cron writes by a blog-scoped database session lock and rechecks event identity before each effect. It uses WordPress's own scheduler functions, verifies committed native state and classifies uncertain/partial outcomes explicitly instead of claiming rollback; unrelated native Cron runners do **not** participate in that lock. The `cron` option still loads into WordPress memory on each operation. Nothing exposes registered event arguments or arbitrary hooks. Since the same public Ability can **cancel** existing events, its mixed-effect MCP annotations explicitly mark it **destructive and not idempotent**, including when a particular request merely lists profiles; UI/security clients must not downgrade trust based on the requested action name.

**Targeted run_now (v0.6.3+).** WordPress Core does not offer a safe targeted executor; Bridge never invokes generic do_action, wp_cron, WP-CLI, shell, or a callback/function/arguments selected by an MCP caller. Without an explicit approved installed-provider runner it still returns cron_run_now_unsupported.

A provider opts in with run_now in the registered actions AND a targeted_runner object implementing WP_AI_Bridge\Support\Cron_Targeted_Runner. Its contract requires run_once(server_context) and independent read-only verify(server_context, effect_ref), an explicitly versioned runner_revision (ASCII 1-64), run_budget_seconds (1-10), and run_destructive boolean. Invalid or incomplete declarations fail closed. The installed provider must implement durable independent business-effect readback and idempotency in BOTH the manual and regularly scheduled callback paths; it must cooperate with its own deadline and small resource limit. PHP executing trusted provider code cannot enforce a hard worker kill, so the budget is a mandatory provider contract and a postcondition check, NOT a generic sandbox or guaranteed preemption.

An authorized caller selects an existing exact native event via profile_id, 64-hex HMAC event_id, and full native expected_snapshot, plus a stable operation_id (8-128 allowed ASCII characters) and confirm=true. No callback/arguments/code are remotely accepted. The scheduled event must be uniquely matched and more than 60 seconds in the future; already-due events are not executed because an uncoordinated WP-Cron worker may be running. Stronger authorization requires BOTH default-off Site Configuration AND Code & Extensions, native manage_options and activate_plugins, and manage_network_options on multisite; a provider-declared destructive effect also requires Users & Destructive. Every grant is rechecked after acquiring the Bridge Cron database lock.

Before any provider effect, Bridge atomically reserves a non-autoload per-site option receipt for the exact **(site, native event)**, independent of the profile ID or runner revision. This permanent event-level claim survives provider profile renames/aliases. Simultaneously registered run_now-enabled profiles with identical immutable hook+args are **all refused** before execution (including conflicting destructive policies); providers must expose a single unambiguous targeted execution authority for that native event. The original principal/client/profile/operation/revision binding still controls verified replay, and a changed profile identity cannot cause re-execution. Its database unique-key INSERT IGNORE is the durable replay fence; WordPress add_option is unsuitable. A separate finite per-site budget of 2,048 retained claims is enforced. Claims are not automatically deleted, because a timed-out, crashed, ambiguous, replayed or long-delayed operation may already have executed. A replay with the identical bound principal/client/operation ID can return already_verified only when the installed provider's persisted effect is verified again; different identities never rerun the same event. A provider exception/timeout, invalid status, verification failure, lost lock, changed native snapshot or lost reply yields cron_run_now_outcome_unknown and permanently reserves the exact event. It never silently retries or fabricates rollback.

A successful provider_verified receipt attests only to a provider-verified durable effect AND unchanged selected native Cron event at that point in time. It does not guarantee future native schedule immutability or prove arbitrary other-provider effects. The original scheduled event remains untouched; later normal callback invocations MUST be deduplicated by the provider itself, using the **same durable business-effect primitive** as run_once. The disposable WordPress acceptance fixture invokes the registered scheduled callback after manual execution and checks the reverse order, confirming one persisted effect. This proves the contract in the test provider, not arbitrary third-party providers.

The feature is absent from v0.6.2 and available in v0.6.3+ under current grants and a deliberately opted-in provider. Neither a plugin installation nor a registered Cron profile proves its specific provider supports targeted execution.

The separate executable acceptance harness is `bash bin/run-issue138-external-mcp-cron.sh`, which starts and **destroys its own disposable Docker WordPress/MariaDB environment**, installs official MCP Adapter 0.7.0 and Bridge, and connects a standards-based Python 2025-11-25 MCP HTTPS client with a temporary OAuth token. It proves external provider discovery, native WordPress schedule/reschedule/unschedule, rejection of arbitrary hooks and stale snapshots, and no spurious callback execution. The test fixture `tests/fixtures/issue138-cron-external-provider.php` must be readable by the WordPress HTTP worker, not just root-only WP-CLI; the harness explicitly makes its disposable MU-plugin file world-readable at mode 0644 after Docker copy. **This fixture and self-signed TLS setup are test-only and must never be installed in production.** The runner proves its test fixture only; it does not prove every third-party Cron provider, installed target or client route behaves identically.

### Site Health (Issue #140; available in published versions)


The site-health Ability reuses the native, filter-aware WordPress Site Health test registry and exposes no generic PHP executor. A bounded action=list returns up to 25 indexed test summaries with total/has_more/next_offset, registry_truncated and status:not_run. A listed test is not automatically executable. Unknown or provider-defined callback tests are disclosed as UI-only unless their exact Core contract is verified; provider-supplied labels are stripped and byte-bounded. Test discovery never executes a diagnostic, network probe or OAuth connection attempt.

action=run requires an exact supported test ID, the default-off Site Configuration group and the current WordPress view_site_health_checks capability. Reviewed Core direct tests use their exact fixed Core methods. Selected Core REST-based tests dispatch through WordPress's local REST server, retaining its controller, route and native per-test permission_callback; no arbitrary provider route or client-chosen function can run. Only the native good/recommended/critical category, sanitized short label, source and UTC observation time are projected, never full debug/server/secret data. A configured HTTP URL cannot prove Internet reachability or a client OAuth connection. The native authorization_header test is intentionally UI-only here because an internal PHP dispatch cannot verify public inbound Authorization-header forwarding. WordPress Tools > Site Health remains the complete native UI. This Ability is included in current public releases; verify the actual installed version, grants and permitted Core test execution on each target. Local integration evidence is not proof of a separate hosted client or Gateway path.

### Project-aware and lossless Workspace (Issue #126 — source-integrated; fresh-client E2E pending)

The existing three Bridge Workspace Abilities remain in place. A stable optional project_ref (1–128 URL-safe ASCII characters) scopes document/task discovery and recovery to one project on the authenticated WordPress site, but does not create a separate security/tenant ACL. Unbound legacy records remain unbound; the Bridge never infers ownership from a title, another project or the latest chat. A site-wide resume reports scope:mixed and deliberately leaves current_focus empty if several projects exist; resume(project_ref) recovers the selected project's active task/next_action/blocker, document keys and actual progress/review/delivery gates. A compact resume includes per-section total/returned/has_more/next_cursor rather than treating an omitted entry as absent.

Use action=list with view=summary, optional project_ref, limit (1–25) and before_id cursor to navigate small ID-ordered summaries, not full Markdown or notes. Legacy unpaged full lists still work when the complete serialized JSON fits the administrator-configured response budget; otherwise they fail with workspace_pagination_required and an actionable continuation. Selected small get calls remain backward-compatible. For long Markdown or task notes request view=summary to obtain id/version/state_hash, then view=window with field=content or notes, byte offset, bounded max_bytes and the exact expected_version/expected_state_hash. The window includes text, total_bytes, next_offset and complete so UTF-8 content can be reconstructed without silent truncation; every part rechecks freshness and permission. Large successful create/update calls return verified committed ID/version/hash with projection_complete:false and omitted_fields, not an oversized potentially lost reply.

Incoming text, Markdown and concise lists are validated before committing: oversize bytes, invalid UTF-8 or sanitization that would remove substantive data cause workspace_lossy_input instead of silent changes. Workspace document and task-note byte ceilings are administrator-configurable per site (defaults 512 KiB per document, 128 KiB per task notes; maximum 1024 KiB and 256 KiB respectively). These are storage quotas, not a guarantee that the current MCP client accepts that much input at once. The 25-list-item and 200-record-per-type ceilings are retained. Both 200-record ceilings now use a fixed per-blog/per-record-type MySQL/MariaDB advisory admission coordinator covering count -> initial WordPress create; concurrent distinct creates cannot independently pass at 199/200. If the coordinator is unsupported/busy, workspace_admission_unavailable blocks the create before effect. A DB session that loses ownership during a WordPress create yields workspace_admission_outcome_unknown with the observed object ID, never a misleading 'nothing happened' claim. Invalid persisted project_ref/key/task enums or malformed optional types fail closed rather than being reinterpreted as legacy; genuinely absent historical fields stay readable. Two optional task fields next_action and blocker are added; legacy data is read unchanged. A project-bound document key is unique within (site,project_ref,key) using the same durable claim mechanism as keyed creates, including archived keys; its binding is immutable. Binding a legacy document requires a current guarded version/hash and an exclusive key claim. Unarchiving uses the same guarded CAS. A complete Workspace export reports actual counts or fails on invalid/overflowed state; it is not an import, migration or tested disaster backup.

### Duplicate-safe create (Issue #128 — source-integrated; not a general exactly-once guarantee)

Only these six Bridge-owned create paths accept an optional client-generated stable operation_id: content-upsert(action=create), media-upload, media-import-url, comment-reply, workspace-document(action=create), workspace-task(action=create). Legacy unkeyed callers remain compatible but have no duplicate-safety claim. The ID must be 8–128 permitted ASCII characters and must be reused unchanged for a retry of the same intention. Different independent intentions must use different IDs.

The durable non-autoloaded WordPress option claim uses a fixed, prepared database INSERT IGNORE against the site's native unique option_name index before the first possibly committing WordPress API. A short-lived, fixed per-site MySQL/MariaDB admission lock serializes count -> unique insertion even for DIFFERENT operation IDs or canonical keys near their independent, finite per-site admission quotas. These named locks use a stable configured WordPress database/schema identity plus the exact current site table and one fixed scope, so independent databases with the same wp_ prefix do not contend, while separate nodes accessing the same schema/site do. A missing/contradictory database identity fails closed instead of guessing. The claim and Workspace coordinators reuse native database named locks only; no caller-selectable SQL/lock names, persistent counter, new data store or public lock Ability exists. Unavailable/unsupported lock acquisition fails closed BEFORE the underlying write; a known duplicate still retains its authorized existing-claim recovery path. WordPress add_option() is deliberately NOT used for exclusivity because Core performs ON DUPLICATE KEY UPDATE. It binds actual blog/site, current authenticated WordPress user, authenticated MCP client ID when available, exact operation and normalized meaningful input fingerprint. Same key/different payload is rejected. A known committed retry only returns fresh authorized object readback; current permissions and object identity are never bypassed. Concurrent or crash/timeout-uncertain outcomes keep their claims and return an explicit unknown/in-progress response with NO blind retry or automatic deletion. A known post-commit featured-media error remains an honest partial outcome with the committed object ID. Claim receipts store only identity hashes, status, ID and timestamps, not content, media bytes or credentials.

Known receipt readback is supported for 30 days. Expired and unresolved claim keys remain permanently reserved to prevent silent duplicate replay; the default generic-operation quota is 2,048 receipts and site administrators can raise it to 100,000 or lower it to 128 via a separate WordPress Settings API option. Canonical document-key receipts retain an independent Workspace-derived quota. Saturation blocks new independent identities, never authorized retry readback of an existing identity; there is no automatic receipt purge. A Workspace Clear does not silently discard these separate durable safety claims. These semantics are bounded duplicate suppression, NOT a universal exactly-once executor for provider REST, OAuth, arbitrary PHP or third-party operations. Real client+WordPress/Gateway and independent assurance must be verified before release.

### Bounded site-context on large sites

`wp-ai-bridge/site-context` with `{}` preserves its original `site`, `current_user`, `theme`, `plugins`, `post_types`, `taxonomies`, `reuse`, and `external_abilities` structure **only when the entire response fits** the configured response JSON budget with reserved protocol headroom and the external Ability hint catalog has no more than 50 entries. No existing small-site field changes. When the combined view would be oversized or silently stop at 50 provider hints, `{}` instead returns just a **fresh** `current_user` (`id` and WordPress native capability booleans) and a `projection` recording `section: "all"`, the reason (`response_budget` or `catalog_limit`), and every omitted section. An omitted section is **not** an empty collection or an unsupported capability.

For a reliable current-principal native authority probe without loading provider inventories, call `{"section":"current_user"}`. This returns the actual current WordPress capability checks including `install_plugins` and `install_themes`; it is **not** Bridge delegation, actual operation authorization, site configuration or proof that installation is possible. Every request checks current **Site Read + WordPress `read`**, and the selected capabilities are recomputed for the current principal. If either permission is revoked, further reads (including pages) are denied.

Other scalar selections: `site`, `theme`, `reuse`. Collection selections: `plugins`, `post_types`, `taxonomies`, `external_abilities`, each accepting `offset` (nonnegative integer, default 0) and `limit` (1–50, default 25). A collection returns its named array plus `page` with `section`, requested `offset`/`limit`, actual `returned`, `has_more`, and `next_offset` **only if more entries remain**. Advance by the returned `next_offset`, which may be less than the requested limit when the encoded page approaches the budget. Results and public provider summaries are evaluated afresh; if WordPress registrations change between requests, restart paging to avoid index drift. `external_abilities` pages use only MCP-public Core/provider metadata (excluding Bridge/Adapter and any hidden Ability) and can reach beyond the legacy first 50; detailed contract inspection remains `abilities-read`.

Untrusted long labels and descriptions are represented by UTF-8-safe bounded prefixes (at most 512 bytes per string); taxonomy object-type lists are capped at 16. Each affected record contains `truncated_fields`, and page metadata reports `projection_truncated`. Selected scalar fields use top-level `projection.truncated_fields`. These are **loss markers**, not reconstructed values, and there is no arbitrary option, private provider metadata, or credential exposure. Invalid input and nonrepresentable pages return typed errors without oversized bodies. See Issue #110 for fixture validation and future live-site confirmation after an authorized deployment.

For large content and transfer contracts, see [Large MCP payloads](./LARGE-PAYLOADS.md).

## Application Password boundary

`Authentication & Credentials` is a separate default-off delegation group. Enabling Users & Destructive, Advanced Metadata, Native Abilities, or another historical group does not enable it implicitly.

The Bridge uses only the fixed WordPress Core Application Password REST route family for an exact user. Core remains authoritative for Application Password availability, multisite membership and the `list_app_passwords`, `read_app_password`, `create_app_password`, `edit_app_password`, `delete_app_password`, and `delete_app_passwords` capability checks.

The generated Application Password is intentionally returned only by `application-password-create`, because Core exposes the plaintext credential only when it is created. The Bridge never persists that plaintext value, never exposes the stored Core hash, and does not include credentials, UUIDs, app IDs, or request payloads in the mutation log. Later list/get/update/revoke responses contain only bounded administrative metadata or deletion confirmation.

Create recovery does not use a Bridge correlation token on `wp_create_application_password` and never treats a public action callback as cleanup provenance. Before any credential-storage snapshot, Bridge runs Core's exact target-specific `create_item_permissions_check()`; this matters because Core's Application Password reader can backfill UUIDs into legacy rows, so an unauthorized request must not trigger that storage normalization. After authorization, Bridge snapshots the exact target and observes the `_application_passwords` pre-write boundary only for the direct Core persistence chain `update_metadata()` → `update_user_meta()` → `WP_Application_Passwords::set_user_application_passwords()` → `create_new_application_password()` → the exact internal `WP_REST_Application_Passwords_Controller::create_item()` request. The nearest metadata write must be that direct Core chain, and the full call stack must contain exactly one matching `WP_REST_Application_Passwords_Controller::create_item()` invocation plus exactly one `rest_do_request()` for the exact request object. A re-entrant/provider `update_user_meta()` call or nested re-dispatch of that same `WP_REST_Request` therefore cannot inherit outer-create provenance. The genuine outer write is accepted only when no earlier metadata filter has already short-circuited it and its proposed state is exactly current state plus one new credential; otherwise that outer persistence attempt is blocked and recovery is required. Bridge retains only that proposed credential's UUID, stored-hash fingerprint and full-item fingerprint in memory. The later exact-request `rest_after_insert_application_password` event remains a success cross-check for the same UUID and Core-formatted one-time password, not cleanup authority.

Cleanup still uses the fixed Core REST DELETE route, but the decisive ownership check is repeated at the actual `_application_passwords` delete persistence boundary. A request-scoped pre-write guard accepts only the direct Core chain ending in `delete_application_password()` → the exact internal `delete_item()` request, requires the currently stored UUID to retain the captured hash/full-item fingerprint, and requires the proposed state to equal current state minus exactly that credential with every unrelated credential unchanged. If REST-lifecycle/provider code changes or replaces the record while retaining the UUID, the Core write is blocked and Bridge returns `application_password_create_recovery_required`; the replacement does not inherit cleanup authority. Successful create still requires final stored state to equal the pre-request baseline plus exactly the captured credential. These checks provide bounded optimistic integrity around the exact Core writes, not serializable isolation: unprovable, nested, re-entrant or externally changed state fails closed rather than widening destructive authority.

This surface does not manage WordPress account passwords, password-reset keys, sessions, cookies, nonces, WP AI Bridge OAuth tokens, or generic authentication metadata. `_application_passwords` remains outside generic user metadata.

## Comments administration boundary

`Comments` is a separate default-off administrator delegation group. Existing Site Read, Builder Write, or other historical grants never enable it on upgrade. Bridge-owned comment operations use only the fixed Core `/wp/v2/comments` collection/item routes through internal `WP_REST_Request` + `rest_do_request()`; callers cannot supply an arbitrary REST route or method, and Core validation plus permission callbacks remain authoritative.

The typed surface is intentionally narrow: bounded list/get, one reply, one moderation/status transition, and one Trash/permanent-delete target. Public list pagination requires an exact post that Core permits the current principal to read, so aggregate totals never span comments on unreadable posts; a positive parent filter is accepted only after that parent itself is readable, approved, standard, and belongs to the same post. Moderation scope retains broader queue pagination for principals with native moderation authority. List/detail results omit author email/IP, user-agent, arbitrary comment meta, avatar payloads, and other hidden transport fields. Comment content is byte-bounded (with an explicit `content_truncated` flag) so a large database row cannot create an unbounded MCP response. Reply input does not expose author identity, IP, status, or metadata overrides. Standard-comment mutations reject non-comment objects such as editor/Core notes.

Trash is permitted under Comments plus exact WordPress authority. Non-force deletion never calls Core DELETE: it uses the status-update lifecycle to move the comment to Trash. Repeating it on an already-trashed comment is idempotent and performs no mutation, so it cannot accidentally become permanent deletion even under a concurrent trash transition. Permanent deletion is reachable only through explicit `force=true` and additionally requires **Users & Destructive** plus WordPress target authority.

## Installed source editing boundary


For a WordPress-installed theme, that inventory can include an existing editable `functions.php` (parent or child theme): `source-files-read` lists/reads the exact file, `source-file-preview` validates an entire proposed replacement, and `source-file-apply` applies the preview-bound candidate only when native `edit_themes`, WordPress file-modification policy, Bridge Code & Extensions + Source Editing grants, file writeability and safe runtime checks allow it. **Registration is not proof of write permission on a particular site.** Prefer a child theme or dedicated feature plugin for durable customizations; never append arbitrary code through an uncontrolled function evaluator.
`Source Editing` is a separate elevated access group and defaults off on both fresh installs and upgrades. Existing `Code & Extensions` consent never enables it implicitly. Source read, preview, apply, and recovery require both groups plus the current WordPress `edit_plugins` or `edit_themes` authority for the selected installed target. WordPress file-modification policy remains authoritative.

Targets are provider-neutral: callers identify one installed plugin main file or theme stylesheet plus one relative editable file. The Bridge starts from WordPress's editable-file inventory, then adds canonical real-path containment. Traversal, symlink escape, arbitrary OS paths, unrelated configuration files, and target switching are rejected. Ordinary discovery returns identities and bounded state only; source bytes are returned only by the elevated exact-read operation.

Preview parses PHP candidates without executing them and returns an exact preimage hash, candidate hash, and target-bound candidate identity. Apply rechecks all of that state immediately before mutation. The fixed-purpose replacement protocol fully stages bytes in a recovery-token-keyed artifact on the exact source filesystem, atomically quarantines the live pathname, verifies the bytes actually moved, and publishes only with hard-link no-replace semantics. If another writer recreates the live pathname, that writer wins and Bridge never overwrites it. Private stage/probe/hold retirement is verified before recovery ownership can be cleared. If an artifact cannot be retired, Bridge keeps recovery ownership and returns recovery-required instead of reporting terminal success. The source filesystem must support hard links plus preservation of the quarantined file's mode/owner/group; unsupported environments fail closed. Persisted bytes are reverified, opcode/theme caches are invalidated as applicable, and FTP/SSH filesystem credentials are never collected.

The concurrency contract follows the installed **pathname/current generation**, not an indefinitely retained descriptor to a superseded inode. Once no-replace publication commits, a file descriptor opened before quarantine still refers to the old generation and cannot overwrite the newly published installed path. Bridge rechecks the quarantined generation before retiring it and preserves any mutation already observable there, but portable PHP exposes no compare-and-unlink primitive and cannot revoke a non-cooperating descriptor opened before the atomic replacement. A process that keeps such a descriptor must reopen the installed pathname before making a later source edit. Bridge does not claim advisory `flock` serializes non-participants.

Active PHP additionally uses WordPress's edited-file scrape protocol against normal WordPress boot without fabricating an administrator session or editor nonce. Missing/invalid scrape sentinels fail closed, including network-active plugin failures that can occur before Core registers the scraper. Runtime failure, explicit recovery, and shutdown recovery all use the same guarded no-overwrite replacement boundary: restoration proceeds only while the candidate still owns the live pathname, and a non-cooperating writer that recreates or changes the path is preserved. Crash reconciliation does not recreate an absent live pathname merely because a known hold exists, because pre-publication absence cannot be distinguished safely from a legitimate post-publication delete/rename. One private bounded recovery record is retained when state or artifact cleanup cannot be verified safely, including across uninstall. Mutation logs contain operation/status metadata only, not source payloads or full diffs.

Explicitly authorized PHP source has normal WordPress-runtime authority. **Source Editing is administrator-level code trust, not a sandbox.**

## Advanced Metadata boundary

`Advanced Metadata` is disabled by default and must be enabled by a WordPress administrator from **WP AI Bridge → Settings**. It is intentionally provider- and object-type-neutral across the bounded post, term, user, and comment metadata surfaces; the Bridge does not maintain provider-specific meta-key allowlists.

Post metadata can target a real WordPress post object when the connected WordPress user may edit that exact object. The post type does not need to be public, REST-exposed, or editor-capable. Bridge-private Workspace types (`wpai_doc` and `wpai_task`) remain explicitly excluded. Revision IDs are canonicalized to their parent post before metadata authorization, physical-state inspection, hashing, or mutation so the authorized object is the object whose post metadata is changed.

Protected/private keys (including keys beginning with `_`) can be reached under that administrator-controlled boundary. When Core or a provider explicitly registers a key or installs a metadata authorization filter, that explicit authorization contract remains authoritative. Protected unregistered keys with no explicit authorization contract may use the exact object's native edit authority once Advanced Metadata is enabled instead of WordPress's generic protected-meta default denial. Additional primitive capabilities or `do_not_allow` injected by `map_meta_cap` remain authoritative.

The generic metadata surface deliberately does not expose arbitrary WordPress options, Bridge Workspace internals, role/capability/session/application-password authority state, or credential-like metadata keys. User and comment metadata additionally require exact native `edit_user` / `edit_comment` authority; multisite and Super Admin boundaries remain WordPress-owned. See [User and comment metadata](USER-COMMENT-METADATA.md) for the bounded user/comment contract.

Credential filtering is provider-neutral and normalizes separator, camelCase, compact, singular, and plural forms for password/secret/credential, API/private-key, OAuth/access/refresh, session, identity/ID, JWT, bearer/auth, and related security-token concepts. Unrelated metadata such as a design token is not blocked merely for containing the word `token`.

`state_hash` is computed from physical stored row identity (physical meta ID plus typed raw stored value) for the exact canonical key, not from registered default expansion and not from a virtual metadata-read short circuit. SQL `NULL` and an empty string are distinct states. An absent registered key and a stored row equal to that key's default are also distinct mutation states.

Existing-row update/delete is bound to the one inspected physical row through an internal fixed-schema, byte-exact compare-and-swap. The raw key/value predicate does not use database text-collation equivalence, and SQL `NULL` is matched with an explicit null branch. Identical or collation-equivalent concurrent rows/values therefore cannot be silently updated/deleted as if they were the inspected bytes.

Verification and compensation remain inside the persistence boundary. If interference is detected before verification completes, update restores only its own unchanged written row and delete restores only its own exact deleted row. The compensating change emits the corresponding WordPress metadata lifecycle actions so observers can reconcile to the final physical state. If the exact compensation predicate no longer matches newer bytes, the Bridge returns a compensation failure instead of overwriting them.

Post metadata creation uses normal WordPress `add_post_meta(..., true)` semantics; user/comment metadata creation uses the corresponding Core metadata lifecycle. Core performs the one sanitizer pass and normal add hooks; the Bridge observes the resulting sanitized value without sanitizing it again. A returned meta ID counts as Bridge-owned only while the exact object/key/raw value is unchanged. If Core's non-atomic uniqueness check races, the Bridge removes only its still-unchanged created row. If an added-metadata observer changes that same row, the Bridge preserves the observer state and returns stale rather than cleaning it up.

The compare-and-swap helpers are not database tools exposed to callers: they accept no caller-controlled SQL, table, column, query fragment, or row ID and are hard-bound to their authorized metadata tables/rows. Their fixed prepared raw update/delete statements exist only to provide byte-exact predicates that WordPress's generic text-column helpers cannot express. Generic SQL/database administration remains absent. This is an optimistic row-level integrity protocol, not a transaction/serializable-isolation guarantee; a later write after the verified operation can immediately make a returned state hash stale.

Metadata values containing PHP objects/resources at any depth, or other values that cannot round-trip through the generic JSON contract without structural loss, are not generically replaceable or deletable. Generic metadata deletion additionally requires **Users & Destructive**.

## Generic term metadata

The same default-off **Advanced Metadata** group controls `term-meta-read`, `term-meta-update`, and `term-meta-delete`. Every request requires both an integer `term_id` and its exact `taxonomy` name. Core categories, tags, and registered custom taxonomies (including non-public/non-REST taxonomies) use the same provider-neutral implementation. There is no taxonomy or meta-key allowlist and no WooCommerce/theme-specific adapter.

The term must resolve unambiguously through WordPress, agree with Core's metadata subtype, and pass `edit_term` for that exact target. Legacy shared term IDs are refused even when a taxonomy was supplied, because the physical term-meta owner and Core capability/subtype resolution would otherwise be ambiguous. Registered metadata and all explicit provider authorization filters remain authoritative. For a protected unregistered key only, a temporary exact user/term/key/operation authorization filter replaces Core's default protected-key denial; it does not remove any final `map_meta_cap` requirement or change the original `user_has_cap` context. This filter is removed before the Ability returns.

Read inputs add `page` (1..10000, default 1) and `per_page` (1..100, default 50). Without a key, items contain **only `key` and `count`**. They never contain values, value-derived hashes, or types. Pagination advances through physical key pages before authorization/secret filtering, so a page may be short or empty while `has_more` is true. Treat `has_more` as navigation, not a total-count promise; concurrent metadata changes may move keys between pages.

A named-key read returns the normal `key`, `count`, `state_hash`, `value_types`, and `values` fields inside `items`. `include_values=true` is allowed only for a named key. Read output also identifies `term_id`, `taxonomy`, `page`, `per_page`, and `has_more`. Exact reads inspect at most two physical rows and reject a multi-row key; listing can still report its count. Read that exact key again immediately before a mutation to obtain `expected_state_hash`.

Update accepts `key`, `value_json`, and `expected_state_hash` in addition to the target. It returns the verified metadata item. Delete accepts `key` and `expected_state_hash`, also requires **Users & Destructive**, and returns `term_id`, `key`, `deleted`, and `state_hash`. Deleting an already absent key with the current empty-state hash returns `deleted=false`.

Term values have a 1 MiB byte bound for submitted JSON and physical/sanitized stored data. PHP objects/enums/resources, excessive depth, non-finite numbers, malformed/non-canonical serialization, reference structures lost by JSON, integer overflow, and JSON object shapes that PHP's array contract would silently change are refused. For example, `{}` and an object consisting only of sequential numeric keys cannot be losslessly mapped by this interface. Safe scalars/arrays still use normal WordPress metadata coercion: a newly stored scalar is normally returned as a string, while SQL `NULL` is a distinct physical state. Existing opaque metadata may be inspected for type/state without exposing its value, but cannot be replaced or deleted generically.

Registered defaults and `get_term_metadata` virtual reads do not determine physical state. Creation preserves Core's one-pass sanitizer, completed `add_term_metadata` filter, native-collation unique precheck, and `add_term_meta`/`added_term_meta` lifecycle around a fixed conditional insertion. The Core wrapper cannot express the target condition in its insert, so the term store owns that bounded physical step without rewriting Core queries. A non-null provider short circuit is refused instead of being treated as ownership of its returned row ID. Keys must fit WordPress's native 255-character column; that storage constraint is not a provider/key allowlist.

Every primary and compensating term-meta insert/update/delete conditions the physical write on the original `term_id`, `taxonomy`, and `term_taxonomy_id`, with a real native term and no second taxonomy owner. The helper writes only termmeta; native terms/taxonomy tables are joined for current identity only. Inserts use a locking source read; updates/deletes retain byte-exact key/value and SQL NULL CAS. No application transaction, schema migration or generic query dispatcher is added.

Create contention removes only the current invocation's unchanged inserted row, including when other rows precede it; an observer-modified row is preserved and reported as stale. The insert ID is captured before added observers run, so a nested/provider-returned ID is not adopted. Compensation retains its pre/post-hook target checks and additionally binds that identity in SQL. Only create cleanup may remove its unchanged orphan when both native term and taxonomy rows have disappeared; it may not touch a transferred live target. Compensation failure requires fresh inspection, not an automatic overwrite/retry.

This is an optimistic row-level integrity protocol, not a transaction or serializable isolation guarantee. A later external write may immediately stale a returned hash. Nothing in these abilities grants arbitrary SQL/options/provider-table access, changes the administrator's group defaults, or deploys a release.

## URL media import

`wp-ai-bridge/media-import-url` requires `url` and `filename`. Optional `post_id`, `title`, `caption`, `description`, and `alt_text` use the normal attachment contract. The result is the same attachment summary returned by `media-upload`. No server path, arbitrary headers, cookies, HTTP method, credentials, or package-install action is accepted.

An administrator must explicitly enable **Remote Media** and **Builder Write**. Existing settings without Remote Media remain disabled on upgrade. The current WordPress principal also needs `upload_files` and authority to edit any supplied parent. Permission is checked before HTTP and again before upload/attachment mutation.

Downloads use `wp_http_validate_url()` and `wp_safe_remote_get()` with native initial/redirect URL validation, verified TLS, a 30-second request timeout, at most five redirects, and uncompressed streaming to a WordPress-generated temporary file. The size limit is the current `wp_max_upload_size()` with a one-byte overflow sentinel, not the in-memory Base64 upload's 20 MiB ceiling. WordPress/hosting network and upload policies remain authoritative.

Only complete HTTP 200 responses with nonempty, permitted-size bytes and a consistent Content-Length (when supplied) are accepted. WordPress validates MIME/extension and creates the attachment and image metadata through its normal lifecycle. Executable filenames are rejected; media import never extracts or installs an extension package. Known temporary files are removed and their removal verified on ordinary success/error paths. A returned attachment-insertion error or revoked authority before insertion also removes this invocation's known uploaded file. Source URLs, response bodies, filesystem paths, and exception messages are not logged or returned as diagnostics.

Unexpected lifecycle or cleanup exceptions return `media_import_recovery_required`. Native error data contains only `attachment_id`, `attachment_state` (`not_created`, `unconfirmed`, or `created`), and `known_cleanup_complete`; the last field describes known cleanup candidates, not transaction rollback or removal of unknown provider effects. An insertion callback can commit before returning its ID, so an interrupted insertion is unconfirmed and its destination is retained rather than blindly deleted. A returned attachment ID is preserved in the recovery message because the supported Adapter forwards error messages but not native error data. Inspect the reported attachment or, for an unconfirmed outcome, the Media Library and upload storage before retrying. Translation/audit failures fall back to a fixed diagnostic-free message; a failed audit cannot be represented as a guaranteed persisted log.


The import adds private/reserved-address checks to native URL validation: all returned IPv4 resolver addresses and available DNS A/AAAA records must pass PHP address validation (including the global-range flag where supported). The same check runs through the native Requests redirect hook, scoped to the invocation-owned stream filename and removed in `finally`; unrelated HTTP requests are not governed by this temporary callback. Core URL/TLS checks and finite redirect limits are not relaxed. The native fixture proves that reserved initial URLs fail before HTTP and reserved redirect targets are refused by the actual Core/Requests hook dispatcher without connecting to those targets. Resolver checks are not DNS pinning: transport re-resolution, a configured proxy, trusted PHP hooks and hosting egress policy remain separate environmental boundaries.

Import is not idempotent: importing the same URL again can create another attachment. An interrupted request is not proof of failure; inspect the Media Library before retrying. This is not a transaction or a sandbox for third-party hooks; process termination and provider side effects may require inspection and recovery. WordPress's own network policy and installed filters remain the runtime trust boundary; the Bridge does not override them or claim to replace host egress controls.

## Inline file-byte reads via ordinary MCP Ability (Issue #134; v0.6.0+)

Published v0.6.0+ provides **wp-ai-bridge/file-bytes-read**, a read-only, source-neutral Ability with an initial media adapter. Its inspect step returns authorized source size/digest and a blog/user/OAuth-client-bound opaque identity. Its chunk step returns bounded Base64 with source-state checks, byte offsets and a stable digest for caller-side verification. Every call requires the enabled Site Read grant, a native attachment read_post capability and confinement to the site's canonical uploads directory. The inline source-size ceiling is operator-tunable and independent of the MCP encoded response ceiling. The legacy one-request Base64 Media upload ceiling is separately configurable with inline_media_upload_mib (20 MiB default; PHP-memory-derived operator maximum), intersected with native WordPress/transport limits, not an aggregate file transport limit.

This is NOT a complete private binary ingress, file transport session, HTTP streaming protocol, WXR artifact export, downloadable model attachment, ChatGPT top-level fileParams extension, or verified Gateway compatibility. This WordPress-side file-byte Ability is included in published v0.6.0+ packages; that does not establish hosted-client native attachment delivery or Gateway interoperability. Do not expose server paths.

## Private transfer administrator recovery (v0.6.0+)

`private-transfer` has an explicit `admin_release` variant, requiring `transfer_id` and `acknowledge_unknown=true` with current WordPress `manage_options` **and** an authenticated OAuth MCP client. It is strictly same-blog and applies only to a `committing`/unknown, one-way claimed native effect. It removes private staging payload/reservation while preserving the immutable claim fence and operation identity; it does not grant access to the original client's private bytes, does not cancel/retry the effect, and returns no owner digest/byte count. This administrator exception is separate from the original user's authenticated, purpose-bound `status/verify/read/append/release/cancel` operations. Revoking Builder Write does not disable administrator cleanup; unrelated site administrators cannot operate across site boundaries. This WordPress-side administrator-recovery implementation is included in published v0.6.0+ packages; site-specific installation, hosted-client attachment delivery and Gateway interoperability require separate acceptance.

## Authenticated private transfer sessions (Issue #134; v0.6.0+, host-dependent private storage)

The implemented `wp-ai-bridge/private-transfer` Ability integrated in main by PR #145 uses existing Bridge OAuth, the registered Core Abilities API and the official MCP Adapter. It can report current configurable inbound message/chunk/file/reserved-disk/concurrency/lease budgets and privately stage client-supplied bytes via begin, append, status, verify, cancel, plus read for frozen Media exports and release for claimed effect receipts. Only current purpose-appropriate native WordPress capabilities and Bridge grants can create or access a lease; every resume binds current site, principal and OAuth client. Unknown/malformed requests, differing replay, stale leases, hash mismatch, revocation, full disk and short writes fail explicitly. No filesystem path is returned, and no staged file is imported or executed.

The input budget is a **per-message** encoded JSON constraint, distinct from total object/file capacity. Current site administrators can adjust the finite separate transfer resource settings without editing source; the PHP host/client/Gateway may impose smaller effective bounds. This WordPress-side private-transfer session Ability is included in published v0.6.0+ packages; hosted ChatGPT attachment/materialization and Gateway integration are unverified. Exact-candidate CI and author-separated HIGH_ASSURANCE approval were completed before PR #145 merged. The separately implemented `wp-ai-bridge/transfer-media-import` Ability consumes only a verified same-client/same-user Media lease into WordPress's native Media Library; it does not execute or unpack archives. A one-way claim fence and journaled checkpoint precede the WordPress side effect. The observed destination_id remains available even when native image editing changes the current file bytes. Scratch copies are independently reserved and crash-reconciled under the stable per-lease lock. After a client timeout, query the transfer status and inspect WordPress's Media Library; NEVER blindly repeat consumption. The Media Library file has normal WordPress sharing semantics and is not automatically private. WXR import, native ChatGPT file attachment materialization, and Gateway transfer compatibility remain separate unverified outcomes.



### Native byte-plane consumers for Media and large content (v0.6.0+)

**Incoming Media:** Call private-transfer(action=limits) to inspect the administrator-owned finite request/chunk/file/session/storage/lease budgets. Begin with purpose=media, the *exact* total_bytes and sha256; send ordered Base64 pieces using action=append with absolute byte offsets. Safe byte-identical replays are acknowledged, conflicting overlaps fail, and status reports exact received_bytes for interruption recovery. After action=verify, call the separately authorized transfer-media-import with the opaque lease ID and an ordinary safe filename. WordPress's own Media MIME, upload, WordPress capability and hosting limits apply. The native Media object is committed only once, with a durable observed destination ID even if WordPress scales a full-size image; source verification uses its original upload where WordPress retains it, not the scaled current Media derivative. Cancel/release the private temporary bytes after verifying the native destination. A ZIP remains passive Media, never plugin execution.

**Outgoing Media:** Call transfer-media-export with an exact native Media attachment ID. Bridge verifies the Site Read grant, current WordPress read_post, active OAuth MCP client and canonical uploads directory; then freezes a digest-bound private snapshot. The result contains transfer_id, total_bytes, sha256, expiry and state, never filesystem paths or public URLs. Iterate private-transfer(action=read,transfer_id,offset,max_bytes), using read_next_offset and read_complete. Each response contains the selected Base64 bytes, byte offset and chunk_sha256. The receiver independently validates each chunk and then the *entire* total length and file SHA-256. Release the private snapshot with action=cancel when its contents have been saved. An inbound staging transfer cannot be read as an outbound file.

**Incoming long text:** Begin a private-transfer with purpose=text and send all UTF-8/Markdown/HTML bytes through the same bounded protocol. Verify its whole digest. A separate effectful transfer-content-commit(action=create,transfer_id,post_type,title,optional status) uses native eligible authoring access, defaulting to a draft. Or action=update requires the exact post_id, expected_modified_gmt and expected_state_hash from a recent content-read; stale edits return a conflict while leaving the verified lease available. Current builder/Live Content/native WordPress rights are mandatory; NUL and invalid UTF-8 are rejected. WordPress post APIs still require the entire value in PHP memory for the final native commit, so the effect fails before claiming if host memory is inadequate. A persistent claim fence prevents blind repeat after a crash. The latest authoritative post state is rechecked under real InnoDB post and metadata row locks across the actual native WordPress write, not merely during a preflight check. Observed transformed bytes are not declared verified exact source bytes. Successful results and status supply the exact WordPress post ID and digest.

The four transfer Abilities are integrated into **main by merged PR #145**, but are **not in published v0.5.1**. Installed WordPress/official Adapter tests have validated the native producer/consumer workflows, but NOT automatic ChatGPT attachment receipt or native model-readable file materialization. A supported external client must reconstruct the returned bytes or use a separately verified client-host attachment mechanism. WXR export/import is a distinct native WordPress producer/consumer under #139, not a second byte transport. Gateway limits, host storage/memory and multi-node private storage are independent compatibility boundaries; no remote cross-repository changes are implied.

## Public Ability contract inspection

**Direct MCP tool inventory versus WordPress operations:** the canonical direct server exposes only the three generic MCP Adapter tools in `tools/list`. Use `mcp-adapter-discover-abilities` to discover public WordPress operations, including `wp-ai-bridge/extension-lifecycle`; absence of that Ability name from `tools/list` alone does not mean it is unimplemented. For a site-specific diagnosis of build version, delegation, native authority and remaining administrator-parity gaps, see [historical administrator-coverage evidence](https://github.com/AChWorks/wp-ai-bridge/issues/99) (v0.5.1, not a current site snapshot).

Use `wp-ai-bridge/abilities-read` with `action: "list"` (the default), optional exact `namespace`, case-insensitive `search` over public name/label/description, `page` (default 1) and `per_page` (default 25, maximum 100). Results sort by exact Ability name and report `total` and `total_pages`; all pages of the current registry are reachable. The registry is a live view, not an immutable snapshot across requests.

An exact `action: "get"` plus `name` returns the provider's actual input/output schemas. An absent native schema stays empty; the Bridge does not invent one. Public name, namespace, label, description, category, MCP type and the three standard boolean-or-null annotations are selected explicitly. Arbitrary provider metadata and callbacks are not returned. Explicit MCP opt-out remains authoritative for both list and exact reads, with no name-guessing bypass. Malformed MCP metadata and non-boolean inherited public flags fail closed, matching the pinned official Adapter exposure rule.

Both actions require **Site Read** and native `read` authority, including when called through the official Adapter. They do not call the target's permission or execute callback. `execution_permission: "not_evaluated"` means the target's real input and current authorization must be checked at execution; public discovery or a read-only annotation is never permission. `bridge-info` remains the source for the current Bridge group settings. The current groups do not uniformly govern all reused provider-native operations; see [architecture and coverage](ARCHITECTURE.md#delegation-boundary).

Responses are bounded to 1 MiB; an oversized or unrepresentable contract returns an explicit error, never a truncated schema. Reduce a list's page size or consult the native provider contract for a larger exact schema. Ordinary lists omit schemas and do not read object values, source files or private site data. Provider-authored public schemas/descriptions are the same public contract data the native inspection interfaces expose; providers must not embed credentials in them.

This capability supplements the existing compact `site-context` reuse hints. It does not implement missing administrative workflows or grant new write/executable authority. Required coverage remains defined by `MASTER-SPEC.md`, with implementation gaps described in `ARCHITECTURE.md`.

## Registered REST route discovery (published #119)

`wp-ai-bridge/rest-routes-read` is a **read-only, explicitly opt-in** inspection Ability. It requires the default-disabled **Registered REST Discovery** group and the current WordPress principal's `manage_options` capability. Existing Site Read, Native Abilities or other grants do **not** enable it, including after upgrading. This inspection Ability never executes a registered REST endpoint. An independently reviewed guarded invocation implementation was merged via [PR #121](https://github.com/AChWorks/wp-ai-bridge/pull/121) and **published in v0.5.1**. Registered REST discovery and invocation Ability registration were verified on a deployed v0.5.1 site, **without executing any generic provider REST handler there**. Both default-off trust grants remain independent of WordPress/provider authorization. See [#119](https://github.com/AChWorks/wp-ai-bridge/issues/119) for the evidence boundary.

Use `action: "list"` (default) with optional `namespace`, `page` (default 1) and `per_page` (default 20; maximum 25). WordPress filters by namespace, then Bridge uses Core's **filtered public route-index aggregation** (`get_data_for_routes`), including `rest_endpoints_description` and `rest_route_data`. Only still-registered, index-visible routes are counted; route removals, argument/method redactions and Core `show_in_index=false` cannot be resurrected. Results include exact registered route names and HTTP methods, in stable sorted order within the current registry snapshot, with `total`, `total_pages`, `has_more` and `execution_permission: "not_evaluated"`. Paging is a live registry view, not a durable snapshot across requests.

Use `action: "get"` and an exact `route` for a selected indexed route. The bounded detail returns endpoint methods and public argument names, primitive `type` where representable, and `required` flags; it intentionally omits provider defaults, values, descriptions, callbacks, raw schemas and secrets. Private/hidden registered routes and unknown routes both return `rest_route_not_found`. Neither list nor get evaluates the endpoint's permission callback or determines target-dependent authorization.

If the selected native registry contains more than **1,024** routes, list fails with `rest_routes_narrowing_required` rather than scanning all public schemas or returning misleading totals; supply a narrower `namespace`. Exact `get` inspects only the matched route's index metadata even on a large site. Native `get_routes()` still performs its own Core registration normalization. All outputs must fit the site administrator-configured MCP JSON response bound. Oversized metadata or unsupported contracts return an explicit error; reduce the list page size or use the provider's native API documentation. A client cannot use route discovery as evidence that it can read or mutate endpoint data. Actual WordPress provider permission callbacks, purpose-specific security controls, Bridge delegation and multisite boundaries remain authoritative. Confirm the **installed** Bridge version and active grants before use; v0.5.1 includes this released discovery Ability.


## Guarded registered REST execution (published #119)

The separate **High-Trust Registered REST Invocation** group defaults **OFF** for new and upgraded installations. When enabled by a WordPress administrator, `wp-ai-bridge/rest-route-invoke` additionally requires the *current authenticated WordPress principal* to have `manage_options`. Site Read, Native Abilities and Registered REST Discovery do not imply this broad execution grant; revoking it denies the next invocation. **Unknown Core/provider REST effects are never classified safe by their path, HTTP method, parameter names or caller declarations.** Until a server-owned, auditable per-effect contract exists, *every* generic execution also requires separate enabled Builder Write, Remote Media, Live Content, Site Configuration, Advanced Metadata, Authentication & Credentials, Code & Extensions, External Packages, Source Editing, Comments and Users & Destructive groups **AND** their mapped WordPress capabilities (edit/publish/upload, activate/install plugins, edit plugin/theme files, moderate comments, delete users, manage options). Missing any protected grant/capability fails **before** running provider index hooks or callbacks and remains revocable. This is an intentionally restrictive, explicitly consented *administrator-equivalent super-trust* mode—not a shortcut around purpose-specific safeguards or a plugin-code sandbox. This independently reviewed implementation is **published in v0.5.1** and discoverable on a verified deployed site, but an actual generic production REST invocation has **not** been tested by that audit. Do not equate release or registration with successful execution under a particular principal/provider.

Inputs are an exact registered local route regex (`route`), the corresponding concrete same-site `path`, an explicit `method` (GET/POST/PUT/PATCH/DELETE) and optional bounded structured `query`/`body` parameters. Example: `{"route":"/wp/v2/posts/(?P<id>[\\d]+)","path":"/wp/v2/posts/7","method":"GET","query":{"context":"view"}}`. The caller cannot supply a host, external URL, arbitrary headers/cookies, raw bytes, request-level authentication token or override method. Local path traversal, unregistered/hidden/index-filtered routes, methods absent from the filtered public contract, and overlapping ambiguous registrations fail closed. In particular, if multiple WordPress handlers share the **same registered route and HTTP method**, invocation fails closed rather than relying on a later public handler when Core will dispatch an earlier hidden/alternate handler. Allowed input argument names are bound to the unique Core-selected handler's filtered index contract (not a union of same-method schemas). This intentionally does not execute provider-private REST routes or reproduce an HTTP browser session.

The native WordPress administrator can adjust the **one-call generic registered REST input budget** under **WP AI Bridge → Settings → Registered REST request input capacity**, independently of the REST authorization switch. Its historical default is **16 KiB**; the finite whole-KiB setting is additionally clamped by the effective **incoming MCP request capacity** (another separate setting), current PHP memory, hosting and client limits. It does **not** change the sensitive-key filters, selected-route identity/capability, 1,024-node and 16-level nesting guards, downstream native Core schemas/permissions, or safe-operation classifications. Increasing one-shot JSON cannot replace the authenticated private-transfer protocol for large files or binary payloads.

A successful preflight dispatches through WordPress Core `rest_do_request(new WP_REST_Request(...))` on the current user/site; Core/provider handlers own the exact permission callbacks, request schema validation and side effects. The Bridge does not evaluate the provider callback directly and does not elevate roles or switch sites. Native response data are rejected if they contain credential-like keys, unsafe objects or exceed the bounded MCP envelope. Raw provider error messages, response headers, tokens and exceptions are not relayed. This is not a complete substitute for provider-side secure handling of credential values and metadata under arbitrary names.

The generic path *cannot* target Bridge/MCP control namespaces, authentication/credential/session endpoints, WordPress Core or provider batch fan-out endpoints (including `/batch/v1`), or Core settings, plugins, themes or user-administration routes. Keep dedicated Bridge capabilities and their separate grants for these operations, as well as source editing, package installation and any future purpose-specific file import/export (#134). As a conservatively mixed-effect Ability its **static metadata is not readonly, is destructive and is not idempotent**, even for GET. Gateway consumers must apply the stronger authorization class rather than infer safety from user-supplied method; any missing Gateway-side support belongs to the single interop Issue #130.

Result fields include native HTTP `status`, an `outcome` and bounded `data` on safe success. `reported_success` indicates only a successful *native HTTP response* for any method; it is not a transaction or effect-classification proof. WordPress providers can attach effects even to GET, so **every** post-dispatch failure, exception or oversized result yields `outcome_unknown`; **do not retry automatically**, even for GET. Inspect the WordPress/provider resource state first. Filtered or denied operations fail before dispatch, with no new access or secret revelation. Generic REST is not an arbitrary HTTP/PHP/SQL/filesystem executor, and WordPress/provider deployment and network policies still apply.

**Review boundary:** Independent HIGH_ASSURANCE delta review of [PR #121](https://github.com/AChWorks/wp-ai-bridge/pull/121) returned COMPLETE/APPROVE for candidate `3d0c5cb0bd9ae897f65ee129fd32f691ac1d490e` after native handler-binding, authorization and E2E evidence remediation. Exact-candidate CI attempt 2 passed 14/14; isolated Gateway-to-WordPress Target execution also passed its tested denied/allowed/revocation and ambiguous-effect paths. The squash merge commit is `44c341b6e30fcdfac34155805bb629eb563ecbce`. Full interactive PKCE onboarding, diverse production plugin densities, published release, production install and the broader #119 acceptance remain unverified/open, not prerequisites retroactively owed by the already approved code review.

### WXR Core producer and authenticated private export (released WordPress-side v0.6.0+)

The main-integrated WXR source contains a WordPress-native producer, `WXR_Export_Stager`, which delegates to Core `export_wp()` and captures output in bounded chunks to an internal `Private_Artifact_Writer`. The writer is content-type-agnostic and may later support other authorized file producers, and is not itself a public file manager, general uploads API or anonymous download service. Its scope is an explicit Core-exportable WordPress content type and finite **caller-provided** per-transfer byte budget; temporary files are owner-only and must resolve outside `ABSPATH` and the web document root. It rejects byte-budget overruns and removes failed partial artifacts, calculates SHA-256 incrementally, and returns a private path solely to an internal WordPress consumer that must delete it. No relative/public URL, client path, editor, auto-import or package installation capability is added.

The native exporter writes XML **and download headers**. Its handler captures XML and restores Core-touched headers before the caller resumes. WordPress Core defines helper functions such as wxr_cdata() globally inside export_wp(), so **only one Core WXR export can execute in any one PHP request**: repeated attempts are rejected with wxr_stage_request_exhausted and must use a separate request; the independent insufficient-budget fixture verifies fail-closed cleanup. Core and provider hooks and the output-buffer/header lifecycle were reviewed for source integration; installed-site operation and external-client attachment delivery still need independent acceptance. The main-integrated `wxr-export-create` Ability connects Core WXR output to the reviewed, merged #134 authenticated, expiring private byte lease with exact SHA-256 and bounded continuation, without a public URL. Exact-source installed WordPress and separate-process localhost HTTPS/OAuth MCP tests exercise the **WordPress-side implementation published in v0.6.0+**; a hosted ChatGPT attachment, Gateway file route and installed production operation need separately verified acceptance.

### WXR verified private ingestion and structural preview (released WordPress-side v0.6.0+)

Main-integrated PR #146 includes `WXR_Import_Preflight` as a **read-only** inspection step and a public `wxr-import-preview` Ability for authenticated verified `purpose=wxr` private leases. It requires native WordPress `import` plus default-off Bridge **Site Configuration**, either a trusted WordPress-generated `Private_Artifact_Writer` owner-only file or an exact private `purpose=wxr` transfer lease bound to the current authenticated client, principal and blog, with exact recorded byte length and SHA-256. Internal PHP callers provide finite **bytes/XML nodes/RSS item** budgets; the public preview derives its finite bounds from the current administrator-owned private-transfer file policy and current PHP integer constraints, not a hardcoded universal file cap. It uses `XMLReader` with network/DTD/entity substitution disabled and rejects DTD/ENTITY references, malformed XML and unsupported WXR 1.2 structure. It emits only size/hash/site and **structural counts** grouped by post type, not a filesystem path or imported records.

**The separate `wxr-import-preview` is structural-only, not an actionable importer plan.** In the main-integrated source, `wxr-import-plan` requires the active **official WordPress Importer 0.9.6**, loaded through the upstream `WP_LOAD_IMPORTERS` bootstrap gate (with WordPress's native post/taxonomy/comment administrative helpers explicitly loaded for the OAuth REST environment), and native WordPress administrator + Bridge Site Configuration and Builder Write. It uses Core's provider parser only after streaming XMLReader preflight and an input limit derived from current PHP memory. It reports source author names/explicit existing-user mapping, CPT counts, current existing-post conflicts, publication count, missing CPT/taxonomy errors and disabled attachment fetch/user creation. Serialized PHP object/reference metadata is refused. Changing source bytes, OAuth client/principal/site, native provider, exact conflicting target IDs, chosen mappings or conflict policy invalidates the HMAC plan token. The native `wp_import_existing_post` callback independently checks exact consented existing target IDs and current privileges immediately before each post effect, rejecting newly raced conflicts or revoked Live Content authority without converting uncertainty into a retry. Current WordPress CPT/taxonomy edit/publish/assign capabilities and default-off Live Content (for published posts and explicit existing-target effects) are checked before permission to execute.

`wxr-import-execute` requires **a separate exact plan token and explicit `confirm=true`**; the verified incoming private WXR lease is durably claimed with immutable fsync + directory fsync **before** the official `WP_Import::import()` effect. An audited adapter subclasses the installed official `WP_Import` only to supply existing-author mappings without trusting PHP `$_POST`, disable user creation/external attachment downloads, and override its **protected metadata decoder**. Official WordPress Importer 0.9.6's default `maybe_unserialize()` applies a global `O:...:` rewrite even inside byte-length-delimited serialized strings, which can change the post-validation grammar. The Bridge's constrained subclass **never rewrites** the metadata: it reuses the exact same bounded primitive/array wire validator immediately before deserializing the **original bytes**, with PHP `allowed_classes=false` as a second guard. Benign O:-looking text inside encoded strings survives as text; O/C/E/r/R structural opcodes fail closed. This is *not* an independent business importer: the owning official provider still handles posts, terms, comments and metadata. The Bridge also denies WordPress HTTP requests during import. Native importer effects are **not atomic**, and the returned result means the provider completed its method, **not** that every imported record succeeded. The private transfer status includes plan hash, processed/post counts and one-way completed/partial/unknown state; NEVER automatically retry a claimed lease, including after a timeout, provider error or interrupted worker. Administrator reconciliation is necessary; no automatic rollback is promised. No client-supplied filesystem path, package installation, public URL, auto-import, Gateway binary handoff or hosted ChatGPT attachment conversion is implied. This public API passed author-separated HIGH_ASSURANCE review and exact-candidate CI before its source merge. It is included in public WordPress-side v0.6.0+ releases; installed-site behavior and hosted ChatGPT/Gateway attachment exchange require separate acceptance.

### Internal native-importer semantic WXR analysis (Issue #139, not an import API)

The main-integrated WXR source also contains `WXR_Native_Import_Plan`, a separate **parser-only** internal diagnostic. It first requires a successful bounded, permission-scoped, exact-byte private WXR preflight; it then optionally calls **only** `WP_Import::parse()` from a verified installed official `wordpress-importer` provider (which WordPress must load via `WP_LOAD_IMPORTERS` before bootstrap). **This internal diagnostic never calls `WP_Import::import()`**; the distinct `wxr-import-execute` Ability above is an explicitly authorized and irreversibly claimed effectful importer consumer, not a parser preview. This input budget is **not a proven PHP peak-memory bound**; callers must size it for their actual PHP memory/time capacity. Larger files can still use the streaming structural inspection and wait for a scalable provider-owned execution plan. No unbounded JSON/base64 transfer or arbitrary WordPress file path is provided.

The summary is informational: Core parser post type/author/term/comment/meta/attachment counts, missing registered CPT/taxonomies, per-blog identity, exact staged SHA-256, potential user/media consent needs, and unresolved conflict warnings. Hosted attachment materialization and verified real-site deployment remain outstanding.

### Administrator-owned high-trust operation content budgets (#147)

**Source Editing for actual large bytes:** Use `source-file-snapshot(kind,extension,file)` to freeze an authorized installed source into an authenticated, exact-SHA-256 private-transfer read lease. Fetch complete, bounded Base64 windows with `private-transfer(action=read,transfer_id,offset,max_bytes)`, verifying length and SHA-256 before use. For large inbound edits, send the desired full candidate through `private-transfer(action=begin,purpose=source_plugin|source_theme,total_bytes,sha256)`, then bounded `append` windows and `verify`. Invoke `source-file-preview-transfer` with the verified `transfer_id` and exact installed target, then `source-file-apply-transfer` with the **same lease and exact preview-returned preimage/candidate hashes and candidate_id**. No arbitrary path or URL is accepted. The lease is one-way claimed before effect, cannot reapply after uncertain completion, and shares the inline Source Editing lock/CAS/recovery machinery. Original inline source read/preview/apply remains for small clients and compatibility; increasing the per-site `source_mib` never changes smaller MCP/client/Gateway request/response envelopes or transfer quotas. The native PHP source parser now verifies a conservative token-memory bound before in-process `token_get_all()` materialization; oversized high-token-density PHP is refused before parsing or writing. A known-safe initial PHP block comment can be omitted *for syntax checking only* without changing saved bytes. Inadequate memory produces a clear no-write error. An unlimited `memory_limit` is not evidence of RAM; WordPress's bounded configured memory is used instead, and absent both no unsafe Source Editing capacity widening is advertised.



On current source (pending a published release), `WP AI Bridge > Settings > High-trust operation content capacity` provides four **separately configurable**, per-site finite operator limits: whole installed plugin/theme source preimage/candidate **2 MiB default**, registered REST setting JSON value **1024 KiB default**, registered REST setting public schema **256 KiB default**, and read-only native Ability catalog JSON response **1024 KiB default**. The complete source edit, target- and hash-bound candidate and crash-recovery preimage still need to fit the PHP process and its operator policy. Schema/value/catalog data stay all-or-unavailable rather than silently truncated; their permissions and provider callbacks do not change. Saving these controls does not change any WordPress/Bridge grant. These are **single-operation in-process capacity policies**, not universal file or transfer caps; direct and Gateway MCP clients may impose smaller encoded request/response limits. Use #134 private authenticated transfer for actual large file movement. The source recovery path independently retains its **previously admitted exact-byte verified limit**, bounded by the current PHP runtime memory envelope, so reducing the source policy does not strand a previously valid pending private recovery claim. New read/preview/apply requests obey the newly lowered policy.

This does not relax the **1 MiB protected physical metadata-row guard** in Term_Meta_Store or User_Comment_Meta_Store. That guard is embedded in bounded physical SQL projection and native serialized-value/CAS handling, not just a preference for one response size. Changing it requires an independently reviewed, separately tested typed SQL/serialization/CAS safety design and a demonstrated real provider need. Metadata keys, native permissions, WordPress/MySQL storage, sensitive-value exclusions, object/ref deserialization, and existing-page-size bounds remain independent. The general catalog list is already paginated; an oversized exact contract remains unavailable rather than returning partial schemas.
